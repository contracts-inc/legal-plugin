## 進め方の原則

**提示形式は `interaction-format.md` に従う**（フォーム形式、質問文の自己完結、進行の単位、出力量）。ここでは質問内容に関する原則のみを示す。

- **選択肢を使う。** 各質問には想定される回答例（選択肢）を用意している。番号で答えられる形にし、当てはまらない場合の記入欄を1つ用意する。
- **セクション単位で進める。** 情報源の確認 → 基本方針 → 条項別基準 → 重大度 → 優先順位 → 運用。異なるセクションの質問を同じフォームに混ぜない。
- **判断材料は数値で添える。** 「過去12件中7件が12ヶ月です」のように件数だけを示す。文書名・条番号・事例の識別子は書かない。
- **「ケースバイケース」は分解する。** 場合分けの軸（金額 / 類型 / 立場 / 相手方属性）を選択肢として示し、判定可能な条件に落とす。
- **未回答は `※要確認` として残す。** 推測で埋めてはならない。
- **回答の根拠を記録する。** 回答者の役割（法務部長 / 法務担当 等）と日付を根拠に残す。
- **個人名を残さない。** エスカレーション先・承認者は役割名で記録する。

## セクション0: 利用できる情報源の事前確認

基準の質は根拠情報の入手可否で決まるため、ヒアリングの冒頭で確認する（`evidence-sources.md` の6系統に対応）。

### 社内規程・既存基準書
- 契約審査基準・契約管理規程はあるか。提供可能か。
- 決裁規程・職務権限規程に契約金額のしきい値が定義されているか。
- 購買規程・外注管理規程はあるか。
- 情報セキュリティ規程・個人情報保護規程はあるか。
- 過去のレビューメモ・法務からの指摘集が蓄積されているか。

### 契約書雛形
- 自社の契約書雛形はあるか。どの契約類型の雛形を持っているか（**扱っている取引形態の特定に使う**）。
- 雛形はどこに保管されているか（法務部門、共有フォルダ、契約管理システム、Google Drive / SharePoint 等）。提供可能か。
- 雛形は自社が作成したものか、相手方から提供されたものか（**自社作成でなければ自社基準の根拠にできない**）。
- 立場ごとに別の雛形があるか（委託者版・受託者版など）。
- 雛形を最後に見直したのはいつか。
- 雛形が無い契約類型はあるか。その類型では相手方の雛形を使っているか。

### 過去契約・交渉実績
- 契約管理システム（CLM）を利用しているか。締結済み契約を検索・参照できるか。
- 契約管理台帳・スプレッドシートはあるか。条項ごとの条件（賠償上限、契約期間、管轄等）が列として記録されているか。
- 過去契約のファイルを個別に提供できるか。何件程度か。
- 交渉経緯がメール（Gmail / Outlook）に残っているか。参照可能か。
- いずれも無い場合、担当者の記憶による妥結傾向を聴取する（**件数の裏付けがないため根拠種別は「ヒアリング」として扱う**旨を伝える）。

### インシデント・トラブル事例
- 契約起因のトラブル事例集・ヒヤリハット集はあるか。提供可能か。
- インシデント管理台帳・クレーム管理台帳はあるか。
- 内部監査報告書・リスクアセスメント結果に契約関連の所見があるか。
- 事例集が無い場合は下記「事例が無い場合の聴取」を行う。

### 事例が無い場合の聴取
- 契約が原因で紛争・クレームになった事例はあるか。原因は何か。
- 委託先・取引先での情報漏洩やセキュリティ事故はあったか。契約に不備があったか。
- 下請法・独占禁止法等に関する行政指摘や内部監査の所見を受けたことはあるか。
- 契約後に想定外の負担（追加費用、無償対応、長期の拘束）が生じた事例はあるか。
- 「この条件を受けたのは失敗だった」と振り返る条件はあるか。
- 現在係争中・調査中の案件はあるか（**ある場合、プレイブックへの反映可否を確認する**）。

### 法令
- 自社に適用される業規制（金融・医療・建設・電気通信・人材等）はあるか。
- 下請法の適用対象となる取引があるか（資本金要件・取引類型）。
- 個人情報の取扱いを伴う契約があるか。越境移転はあるか。

### レビュー実績・版更新記録（改訂時）
- 契約管理システムで過去のレビュータスク・レビュー完了コメントを参照できるか。
- 版更新時の変更理由（更新コメント）が記録されているか。参照できるか。
- 前回のプレイブック改訂はいつか（**分析対象期間の起点になる**。不明な場合は直近1年を既定とする）。
- レビュー担当者は何名か（担当者ごとに判断がばらついている可能性を確認する）。
- 年間のレビュー件数はどの程度か（改訂候補の件数しきい値の調整に用いる）。

## セクション1: 基本方針（§1）

### 1.1 自社の立場と優先事項

**取引形態の棚卸し（条件付きセットの選択に使う）**
- 締結している契約の類型を挙げてほしい。選択肢: 業務委託（準委任 / 請負）/ NDA / SaaS・クラウド / ライセンス / 売買・製造 / 販売代理・OEM / 共同研究開発 / 保守・運用 / 人材派遣・紹介 / 賃貸借 / 広告・制作 / 建設工事 / その他。
- それぞれで自社はどちらの立場か。選択肢: 委託者 / 受託者 / ベンダー / 顧客 / ライセンサー / ライセンシー / 売主 / 買主 / 開示者 / 受領者 / 双方。
- 件数が多い順に3つ挙げるとどれか（**基準を作り込む優先順位になる**）。
- 相手方の雛形を使うことが多いか、自社の雛形を使うことが多いか。選択肢: ほぼ自社雛形 / ケースにより異なる / ほぼ相手方雛形。

**審査の対象と体制**
- 契約審査の対象範囲は。選択肢: 全件審査 / 金額基準以上のみ / 非定型のみ / 事業部門の依頼ベース。
- 法務の体制は。選択肢: 専任の法務部門 / 兼任担当者 / 外部弁護士に依存 / 事業部門が一次審査。
- 年間の審査件数はどの程度か。

**方針**
- リスク許容度は。選択肢: 保守的（リスク回避優先）/ 中程度（バランス）/ 事業スピード優先。
- 判断に迷ったときはどちらに倒すか。選択肢: 安全側（厳しく）/ 取引成立側（緩く）/ 都度エスカレーション。
- 交渉スタンスは。選択肢: 強く主張する / 公平合理的な条件を追求する / 相手方の雛形を尊重し重要点のみ修正。
- 相手方の属性で方針が変わるか。選択肢: 大企業 / 中小企業 / スタートアップ / 官公庁・自治体 / 海外企業 / 個人事業主。変わる場合は属性ごとの違いを確認する。
- 取引の継続性で方針が変わるか。選択肢: 継続取引は緩め / 単発取引は厳しく / 変わらない。

### 1.2 エスカレーション基準

- 契約金額のしきい値はいくらか。複数段階ある場合はすべて確認する（例: 1,000万円 / 5,000万円 / 1億円）。
- 各しきい値の承認者は誰か（**役割名で記録する**）。選択肢: 法務担当 / 法務責任者 / 事業責任者 / 管掌役員 / 経営会議 / 取締役会。
- 金額以外でエスカレーションが必要な条件は何か。選択肢: 賠償上限なし / 知財の全面譲渡 / 準拠法が外国法 / 反社条項の拒否 / 独占・専属の付与 / 個人情報の越境移転 / 契約期間が3年超 / 中途解約不可 / 相手方雛形をそのまま使用 / 前例のない類型。
- 「契約締結不可」と判断できるのは誰か。
- 契約期間・更新でエスカレーションが必要になる条件はあるか（自動更新の累計、長期拘束）。
- 決裁規程・職務権限規程に既定があるか。あれば規程名と条番号。
- エスカレーション後の記録はどこに残すか。選択肢: 契約管理システム / 稟議システム / メール / 台帳 / 残していない。
- エスカレーションの所要時間はどの程度か（実務上の負荷。RED判定を増やすかの判断材料になる）。

## セクション2: 条項別基準（§2.x）

各条項について、共通して以下の3点を確認する。

1. **自社基準:** 目指す条件は何か（数値・条件で）。
2. **許容できない条件:** これに該当したら受諾しない・エスカレーションする、という境界はどこか。
3. **フォールバック:** 第一希望が拒否された場合、どこまで譲歩できるか。

立場によって基準が変わる条項は、**立場別に分けて確認する**（例: 委託者としての基準と受託者としての基準）。

### 2.1 損害賠償の制限

- 賠償上限の算定基礎は。選択肢: 直近12ヶ月の対価 / 直近6ヶ月の対価 / 直近3ヶ月の対価 / 契約総額 / 定額（金額を確認）/ 上限なし。
- 上限の許容範囲は（下限〜上限）。
- 上限は相互適用が必須か。選択肢: 相互必須 / 片務も許容 / 自社が受ける側のみ上限を要求。
- 上限の除外事由として許容するものは。選択肢: 故意・重過失 / 守秘義務違反 / 知財侵害 / 人身損害 / データ漏洩 / 法令違反 / 第三者への支払義務 / 反社該当。
- 除外事由に上限を設けるか。選択肢: 完全に無制限 / 通常上限の2倍等の別枠上限 / 除外を認めない。
- 特別損害・間接損害・逸失利益の免責は必須か。選択肢: 必須（相互）/ 必須（自社のみ）/ 任意。
- データ復旧費用・事故対応費用（調査・通知・信用回復）を賠償範囲に含めるか。
- 賠償請求できる期間の制限（請求期限）を設けるか。選択肢: 1年 / 2年 / 法定の時効による / 定めない。
- 上限なし（青天井）を受諾する余地はあるか。あるとすればどの条件下か。

### 2.2 補償 / 損害賠償の範囲

- 補償義務は相互が原則か。選択肢: 相互必須 / 片務も許容（条件を確認）/ 補償条項を置かない。
- 補償の対象範囲は。選択肢: 第三者からの知財侵害クレームに限定 / 第三者クレーム全般 / 契約違反全般 / いかなる違反も対象（包括）。
- 補償額に責任上限を適用するか。選択肢: 適用する / 適用外を認める（条件を確認）/ 別枠上限を設ける。
- 防御権・和解権の帰属は。選択肢: 被補償者に帰属 / 補償者に帰属（被補償者の同意が必要）/ 協議による。
- 補償請求の手続要件を定めるか（通知期限、協力義務）。
- 知財侵害クレームの場合、代替品提供・回避設計・返金のいずれを求めるか。

### 2.3 知的財産権

- バックグラウンドIP（既存知財）の扱いは。選択肢: 各当事者が留保（譲渡不可）/ 一部譲渡を許容 / 議論しない。
- フォアグラウンドIP（成果物）の帰属先は。選択肢: 委託者に全部帰属 / 受託者に帰属し委託者にライセンス / 共有 / 対価に応じて個別判断。
- 著作権法第27条・第28条の権利移転の明記は必須か。選択肢: 必須 / 望ましい / 不要。
- 著作者人格権の不行使条項は必須か。選択肢: 必須 / 「正当な理由なく行使しない」等の努力義務で可 / 不要。
- 受託者側に残すライセンスの範囲は。選択肢: 自社業務での再利用可 / 汎用モジュールのみ再利用可 / 再利用不可。
- 汎用的なノウハウ・ツール・ライブラリの取扱いに方針はあるか。
- 第三者の知財（OSS、商用ライブラリ）を成果物に含める場合の事前承諾を要求するか。
- 特許を受ける権利・職務発明の扱いを定めるか（共同開発時は類型別も参照）。
- 競合他社への独占ライセンス付与を認めるか。

### 2.4 データ保護とセキュリティ

- 個人情報を取り扱う契約で必須とする条項は。選択肢: 委託先監督 / 目的外利用の禁止 / 安全管理措置 / 従業者の監督 / 再委託の制限 / 事故報告 / 終了時の返還破棄 / 監査権。
- 再委託の可否形式は。選択肢: 事前の書面承諾 / 事前通知（異議なければ承諾）/ 包括同意 / 禁止。
- 再委託先に同等義務を課すことを要求するか。
- 漏洩事故の報告期限は何時間以内か。選択肢: 24時間 / 48時間 / 72時間 / 速やかに（数値なし）。許容範囲も確認する。
- 事故時の費用負担（調査・通知・信用回復）の分担方針は。
- 契約終了時のデータの取扱いは。選択肢: 返還 / 破棄 / 返還または破棄を選択 / 破棄証明書の提出を要求。
- データの保存場所・保存期間に要件はあるか（国内限定、ログ保存期間等）。
- 越境移転がある場合の追加要件は。選択肢: 移転先国の特定を要求 / 同等の保護措置を要求 / 本人同意を前提 / 越境を認めない。
- セキュリティ監査権はどこまで求めるか。選択肢: 現地監査 / 書面・質問票による確認 / 第三者認証（ISMS / SOC2）の提出で足りる / 求めない。
- 求める第三者認証・準拠基準はあるか（ISMS、Pマーク、SOC2、ISO 27017 等）。
- 秘密情報と個人情報を別条項で扱うか、まとめるか。

### 2.5 契約期間と解除・反社条項

- 当初契約期間の標準は。選択肢: 6ヶ月 / 1年 / 2年 / 3年 / 案件ごと。
- 自動更新を認めるか。選択肢: 認める / 認めない（更新は都度合意）。
- 更新拒絶の通知期限は。選択肢: 1ヶ月前 / 2ヶ月前 / 3ヶ月前 / 6ヶ月前。許容範囲も確認する。
- 中途解約権は必須か。選択肢: 必須（無条件）/ 必須（違約金付きで可）/ 不要。
- 中途解約の予告期間は何ヶ月か。許容範囲も確認する。
- 違約金・残期間分の支払義務を受諾するか。選択肢: 一切認めない / 残期間の一部まで許容 / 全額を許容。
- 催告解除の催告期間は。選択肢: 14日 / 30日 / 相当期間（数値なし）。
- 無催告解除事由として必須とするものは。選択肢: 破産・民事再生等の法的整理 / 反社該当 / 重大な守秘義務違反 / 支払停止 / 差押え / 事業譲渡・支配権の変動 / 許認可の取消。
- 反社会的勢力の排除条項は必須か。選択肢: 必須（欠如は締結不可）/ 望ましい / 相手方の規程で代替可。
- 支配権の変動（M&A）を解除事由または承諾事由とするか。
- 契約上の地位・権利義務の譲渡を禁止するか。選択肢: 事前承諾を要する / 包括承継は例外的に許容 / 禁止しない。
- 存続条項の対象と期間は。選択肢と期間を確認: 秘密保持（1年 / 3年 / 5年 / 無期限）/ 損害賠償 / 知財 / 準拠法・管轄 / データの返還破棄。
- 解除時の清算方針（既履行分の対価、成果物の引渡し、データ移行協力）を定めるか。

### 2.6 準拠法と紛争解決

- 準拠法の標準は。選択肢: 日本法 / 相手方所在国法も許容 / 第三国法も許容。
- 他国法を受諾する余地はあるか。ある場合エスカレーション対象か。
- 紛争解決手段は。選択肢: 訴訟 / 仲裁 / 調停前置のうえ訴訟 / 協議のうえ訴訟。
- 管轄裁判所の標準は。選択肢: 東京地方裁判所 / 大阪地方裁判所 / 自社本店所在地 / 被告地。専属的合意管轄とするか。
- 許容できる他の裁判所はあるか。
- 仲裁を受諾する場合の条件は。選択肢: 仲裁機関（JCAA / ICC / SIAC / AAA 等）/ 仲裁地 / 使用言語 / 仲裁人数。
- 少額紛争について簡易な解決手続を設けるか。
- 弁護士費用の負担方針は。選択肢: 各自負担 / 敗訴者負担 / 定めない。
- 契約書の言語と正文はどちらか（英文併記時の優先関係）。

## セクション3: 重大度分類（§3）

- GREEN / YELLOW / RED の3分類でよいか。自社の既存のリスク分類体系があるか。
- 各分類の対応アクションは。選択肢: GREEN=認識のみ / YELLOW=交渉 / RED=エスカレーション。異なる運用があれば確認する。
- YELLOW と RED の境界を分ける最も重要な判断軸は何か。選択肢: 金額規模 / 法令違反の有無 / 事業継続への影響 / 前例の有無 / 相手方の交渉余地。
- セクション0 で聴取した事例、または提供された事例集のうち、RED の具体例に反映すべきものはどれか（**匿名化・一般化して反映する**）。
- 相手方から繰り返し要求され、毎回判断に迷う条件はあるか。
- GREEN と判定してよい「軽微な差異」の範囲はどこまでか（例: 基準値の±10%以内）。
- 複数の YELLOW が重なった場合の扱いは。選択肢: 個別に判断 / 一定数以上で RED に格上げ / 総合的にエスカレーション。
- RED でも締結を優先する例外はあるか。ある場合、誰の承認で可能か。

## 回答が得られない場合の扱い

| 状況 | 対応 |
|---|---|
| 「決まっていない」と回答された | 実績レンジまたは一般的な商慣行を提示して仮の値を選ばせる。選べない場合は `※要確認` を残す |
| 「ケースバイケース」と回答された | 場合分けの軸（金額 / 類型 / 立場 / 相手方属性）を提示し、条件に分解する。分解できない場合は `※要確認` |
| 回答者に決定権がない | 決定権者（役割名）を確認し、`※要確認（決定権者: 〇〇）` として残す |
| 回答が既存の社内規程と矛盾する | どちらを採用するかを確認する。勝手に一方を採用してはならない |
| 回答が法令上の強行規定に反する | 該当条文を示して指摘し、法令要件を下限として設定する |
| 質問の意図が伝わらない | 具体的な条項例・トラブル例を挙げて言い換える。専門用語を避ける |
