# レビュー用出力とフィードバックの取り込み

> **このファイルについて:** 人がプレイブックをレビューしやすい形で出力し、書き込まれたフィードバックを取り込むための規約です。Markdown の生テキストをレビューさせないこと、レビュー観点を絞ること、フィードバックを機械的に回収することを目的とします。

## Contents

- 原則
- 1. 出力するファイル
- 2. playbook.docx の体裁
- 3. review-sheet.csv の列定義

- 5. フィードバックの取り込み
- 6. 反映と再出力
- 7. 禁止事項

## 原則

1. **Markdown の生テキストをレビューさせない。** 通読は Word（`playbook.docx`）で行う。
2. **全文通読を前提にしない。** 決定事項の一覧（`review-sheet.csv`）を併せて渡し、確認ポイントを絞る。
3. **フィードバックは機械的に回収する。** Wordコメント・変更履歴・レビューシートを `scripts/extract_review_feedback.py` で抽出し、目視の読み取りに依存しない。

---

## 1. 出力するファイル

3つを常に出力します。**どの形式でレビューするかをユーザーに質問してはなりません**（Word が使える環境かどうかは、ファイルを渡してから本人が選べばよい）。

| ファイル | 用途 | 使う人 |
|---|---|---|
| `playbook.docx` | レビュー用の本文。Wordコメント・変更履歴で指摘を書き込んで返してもらう | レビュー担当者（既定） |
| `review-sheet.csv` | 決定事項の一覧。`対応` 列に承認/修正/保留を記入して返してもらう。**Word が使えない場合のフォールバック**（Excel / Google スプレッドシート / テキストエディタで開ける） | レビュー担当者 |
| `playbook.md` | `review-contract` に渡す本体。レビュー依頼時に添付する形式 | スキル間の連携用 |

案内は次の1文で足ります。

> レビューは `playbook.docx` にコメントや変更履歴を入れて返していただく方法と、Word が使えない場合に `review-sheet.csv` の「対応」列を記入していただく方法のどちらでも構いません。

---

## 2. playbook.docx の体裁

`playbook.md` と同じ内容・同じ節番号で、Word の書式を適用して出力します。

| 要素 | 体裁 |
|---|---|
| §1〜§6 の節見出し | 見出し1 |
| §1.1、§2.1 などの小見出し | 見出し2 |
| GREEN / YELLOW / RED、Tier 1〜3 の見出し | 見出し3 |
| 自社基準 / 許容できない条件 / フォールバック のラベル | 太字。配下は箇条書き |
| エスカレーション基準、改訂履歴 | 表（罫線あり、見出し行を強調） |
| 根拠の注記 | 本文より1段小さい文字。灰色 |
| `※要確認` | **太字＋赤字**。レビュー時に目に留まるようにする |
| 修正案フォーマットのコードブロック | 等幅フォント、背景に薄いグレー |

**先頭に注記を入れる。** 1ページ目の冒頭に、メタデータブロック（版数・最終更新日時・承認者・承認日・次回見直し予定・対象範囲）を表として配置し、「本ファイルはレビュー用であり、確定版ではない」旨を記載する。**最終更新日時は次回改訂の情報収集の起点になるため、必ず含める。**

**目次を付ける。** 節が多いため、先頭に目次（見出し1〜2）を配置する。

**コメントや変更履歴をスキル側で入れてはならない。** `playbook.docx` は白紙の状態で渡し、書き込むのは人だけとする（`review-contract` が生成するレビュー結果の docx とは役割が異なる）。

## 3. review-sheet.csv の列定義

決定事項を1行1件で並べます。**列名は以下のとおり固定**します（`scripts/extract_review_feedback.py` がこの列名で読み取るため）。

| 列 | 内容 | 記入者 |
|---|---|---|
| `#` | 連番 | スキル |
| `節` | 対応するプレイブックの節番号（例: 2.1） | スキル |
| `項目` | 何についての基準か（例: 賠償上限） | スキル |
| `決めた基準` | 確定した内容。数値・条件で簡潔に | スキル |
| `根拠` | 出所と件数（例: 実績12件中7件、ヒアリング、下請法第4条） | スキル |
| `対応` | **承認 / 修正 / 保留** のいずれかを記入 | レビュー担当者 |
| `コメント` | 修正内容や保留理由 | レビュー担当者 |

- **`対応` と `コメント` は空欄で出力する。** ここが記入欄であることが分かるようにする。
- 文字コードは **UTF-8（BOM付き）** で出力する。Excel で開いた際の文字化けを避けるため。
- 1行が長くなりすぎないよう、`決めた基準` は80文字程度に収める。詳細は `playbook.docx` 側にある。
- `※要確認` の項目も行として含め、`決めた基準` に `※要確認` と記載する。レビュー担当者に埋めてもらえる。

## 4. レビュー依頼の伝え方（観点の明示）

「全体を確認してください」と依頼してはならない。**見てほしい観点を3点程度に絞って提示**する。観点が絞られていないとレビューされない。

観点は次から、その回の作成内容に応じて選ぶ。

| 観点 | 提示する場面 |
|---|---|
| 実績から導いた許容範囲が実務に合っているか | 過去実績を根拠に基準を設定した場合 |
| RED 判定の境界が厳しすぎ／緩すぎないか | 重大度分類を新設・変更した場合 |
| エスカレーション先と金額しきい値が現在の決裁権限と合っているか | §1.2 を設定した場合 |
| `※要確認` の項目（n件）を埋められるか | 未確定項目が残っている場合 |
| 事例から導いた「許容できない条件」が過剰でないか | インシデント事例を反映した場合 |
| 緩和した基準が妥当か | モードBで基準を緩めた場合 |
| 追加した条項が自社の取引実態に合っているか | §2.7 以降を追加した場合 |

依頼文の例（`interaction-format.md` の引用禁止に従い、文書の引用や条番号の参照を含めない）。

> レビューをお願いします。特に次の3点をご確認ください。
> 1. 賠償上限の許容範囲（6〜24ヶ月）が実務に合っているか
> 2. 個人情報の再委託を「受諾不可」としたのが厳しすぎないか
> 3. 未確定の12件を埋められるか

## 5. フィードバックの取り込み

返却されたファイルを `scripts/extract_review_feedback.py` で抽出します。**目視で読み取ってはなりません**（取りこぼしを防ぐため）。

```bash
# Word でレビューされた場合（コメント・変更履歴・表を抽出）
python scripts/extract_review_feedback.py reviewed.docx

# レビューシートで返された場合
python scripts/extract_review_feedback.py review-sheet.csv

# 内容を目で確認したい場合
python scripts/extract_review_feedback.py reviewed.docx --format text
```

標準ライブラリのみで動作し、追加のインストールは不要です。

### 出力の扱い

| 抽出結果 | 意味 | 対応 |
|---|---|---|
| `comments` | Wordコメント（指摘の本文と対象箇所） | 指摘ごとに反映方針を判断する |
| `tracked_changes` | 変更履歴（挿入・削除された文字列） | 文言の修正としてそのまま反映を検討する |
| `decisions` で `action` が `approved` | 承認 | そのまま確定する |
| `decisions` で `action` が `revise` | 修正指示 | `comment` の内容を反映する |
| `decisions` で `action` が `hold` | 保留 | `※要確認` に戻す |
| `decisions` で `action` が `unanswered` | 未記入 | 追加確認の対象にする |
| 上記以外の `action` の値 | 想定外の記入 | 記入内容を確認する |

### 判断が必要な場合
指摘の意図が読み取れない、または複数の反映方法がある場合は、`interaction-format.md` の選択フォームで確認する。**コメントの文面を引用せず**、論点を平易な言葉で書く。

避ける書き方: 「『SaaS契約では6ヶ月が実態に近い』とのコメントがありました。どうしますか」
推奨する書き方: 「賠償上限の許容範囲の下限を6ヶ月に緩めますか」

## 6. 反映と再出力

1. `approved` の項目を確定する。
2. `revise` と Wordコメント・変更履歴の指摘を反映する。
3. `hold` と `unanswered` を `※要確認` として残す。
4. 3ファイル（`playbook.docx` / `review-sheet.csv` / `playbook.md`）を**再出力**する。**内容を変更した場合はメタデータブロックの最終更新日時を更新する**（体裁のみの再出力では更新しない）。
5. チャットでは「反映した件数、未確定として残した件数」を2文以内で示す。**プレイブック全文や反映内容の一覧をチャット本文に貼らない。**
6. 再出力したファイルで再レビューを依頼する場合、**前回からの変更点だけを観点として提示**する（全体の再通読を求めない）。
7. `※要確認` が残っていても、法務責任者の承認が得られれば確定してよい。残件は次回改訂の対象として引き渡す。

## 7. 禁止事項

- **【禁止】** Markdown ファイルだけを渡してレビューを依頼すること。
- **【禁止】** どの形式でレビューするかをユーザーに質問すること（3ファイルを常に出力する）。
- **【禁止】** 「全体を確認してください」とだけ依頼すること（観点を3点程度に絞る）。
- **【禁止】** 返却された Word コメントや変更履歴を目視で読み取って反映すること（抽出スクリプトを使う）。
- **【禁止】** `playbook.docx` にスキル側でコメント・変更履歴を書き込むこと。
- **【禁止】** `review-sheet.csv` の列名を変更すること（抽出スクリプトが読めなくなる）。
- **【禁止】** 反映内容の一覧やプレイブック全文をチャット本文に提示すること。
