# レビュー用出力とフィードバックの取り込み

> 人がプレイブックをレビューしやすい形で出力し、書き込まれたフィードバックを取り込むための規約。

## 原則

1. **レビュー形式はユーザーに事前に選ばせる。** 生成に入る前に選択フォームで確認する（§1）。
2. **渡すのは1形式だけ。** 複数の形式を同時に渡すと、指摘が複数のファイルに分散する。
3. **全文通読を前提にしない。** 確認ポイントを3点程度に絞って渡す（§4）。
4. **フィードバックは機械的に回収する。** Wordコメント・変更履歴・レビューシートを `scripts/extract_review_feedback.py` で抽出し、**目視の読み取りに依存しない**。

---

## 1. レビュー形式の選択

**レビュー用ファイルを作る前に、どの形式でレビューするかを選択フォームで確認します。** 誰がどのツールでレビューするかは組織の運用によって変わるため、スキルが決めるべき事項ではありません。

| 選択肢 | ファイル | 指摘の書き込み方 |
|---|---|---|
| **1. Word（推奨）** | `playbook.docx` | Wordコメント・変更履歴 |
| **2. 表計算ソフト** | `review-sheet.csv` | `対応` 列に承認 / 修正 / 保留を記入（Excel / Google スプレッドシートで開ける） |
| **3. チャット上で確認** | Markdown の表（`review-sheet.md`） | 表の `対応` 列に記入、またはチャットで番号回答 |

聞き方は次のとおり。**この1問だけを単独のフォームで出す。**

```
## レビュー方法の確認（1問）

プレイブックの内容が固まりました。次にレビュー用のファイルをお渡しします。

**Q. どの形式でレビューしますか**
1. Word ファイル（推奨。コメントや変更履歴で指摘を書き込めます）
2. 表計算ソフト用の CSV（決定事項の一覧に、承認 / 修正 / 保留を記入する形式）
3. チャット上の表（ファイルを開かず、この場で番号でお答えいただく形式）
4. おすすめに任せる

番号でお答えください。
```

- **「4. おすすめに任せる」を選ばれた場合は Word を既定とする。**
- **選ばれた形式を生成できない場合**（ランタイムに文書生成機能がない等）は、その旨を1文で伝えて次の形式に切り替える（Word → CSV → Markdown の表）。**体裁が作れないことを理由に出力を止めてはならない。**
- **レビュー往復の途中で形式を変えない**（書き込み先が変わると混乱する）。再出力は前回と同じ形式で行う。**セッションをまたいで前回の形式が分からない場合は、再度この形式で確認する。**
- **`※要確認` の一覧・根拠・差分は、レビュー用ファイルとは別にファイル出力する**（`SKILL.md` ステップ5.3）。これらは記入対象ではなく参照用のため、1形式の制約の対象外。

### playbook.md（`review-contract` 連携用）の扱い

`playbook.md` は**レビュー用ファイルではなく、`review-contract` に渡す成果物**です。**承認が確定した時点で出力**します（レビュー段階では出力せず、これだけを渡してレビューを依頼してもなりません）。

レビュー担当者から「全文を読みたい」と要望があった場合に限り、CSV・Markdown の表を選んだときに `playbook.md` を追加で渡します。要望を先に尋ねることはしません。

### 案内文

案内は次の1文で足ります（渡した形式に合わせる）。

> レビューは `playbook.docx` にコメントや変更履歴を入れて返してください。

---

## 2. playbook.docx の体裁

`playbook.md` と同じ内容・同じ節番号で、Word の書式を適用して出力します。

**生成手段:** ランタイムの文書生成機能で作成します（`review-contract` がレビュー結果の docx を作成するのと同じ手段）。**本スキルは docx 生成用のスクリプトを同梱しません。** 生成できない場合は §1 に従って CSV に切り替え、その旨を1文で伝えます。**体裁が作れないことを理由に出力を止めてはなりません。**

| 要素 | 体裁 |
|---|---|
| §1〜§6 の節見出し | 見出し1 |
| §1.1、§2.1 などの小見出し | 見出し2 |
| GREEN / YELLOW / RED、Tier 1〜3 の見出し | 見出し3 |
| 自社基準 / 許容できない条件 / フォールバック のラベル | 太字。配下は箇条書き |
| エスカレーション基準、改訂履歴 | 表（罫線あり、見出し行を強調） |
| 根拠の注記 | 本文より1段小さい文字。灰色 |
| `※要確認` | **太字＋赤字**。レビュー時に目に留まるようにする |
| 修正案フォーマットのコードブロック | 等幅フォント、背景に薄いグレー |

**先頭に注記を入れる。** 1ページ目の冒頭に、メタデータブロック（版数・最終更新日時・承認者・承認日・次回見直し予定・対象範囲）を表として配置し、「本ファイルはレビュー用であり、確定版ではない」旨を記載する。**最終更新日時は次回改訂の情報収集の起点になるため、必ず含める。**

**目次を付ける。** 節が多いため、先頭に目次（見出し1〜2）を配置する。

**コメントや変更履歴をスキル側で入れてはならない。** `playbook.docx` は白紙の状態で渡し、書き込むのは人だけとする。

## 3. review-sheet.csv の列定義

決定事項を1行1件で並べます。**列名は以下のとおり固定**します（`scripts/extract_review_feedback.py` がこの列名で読み取るため、変更してはならない）。

| 列 | 内容 | 記入者 |
|---|---|---|
| `#` | 連番 | スキル |
| `節` | 対応するプレイブックの節番号（例: 2.1） | スキル |
| `項目` | 何についての基準か（例: 賠償上限） | スキル |
| `決めた基準` | 確定した内容。数値・条件で簡潔に | スキル |
| `根拠` | 出所と件数（例: 実績12件中7件、ヒアリング、下請法第4条） | スキル |
| `対応` | **承認 / 修正 / 保留** のいずれかを記入 | レビュー担当者 |
| `コメント` | 修正内容や保留理由 | レビュー担当者 |

- **`対応` と `コメント` は空欄で出力する。** ここが記入欄であることが分かるようにする。
- 文字コードは **UTF-8（BOM付き）** で出力する。Excel で開いた際の文字化けを避けるため。
- **返却は `.csv` のままでも、Excel で開いて `.xlsx` として保存されたものでも受け取れる**（抽出スクリプトが両方に対応）。**保存形式をユーザーに指定させない。**
- 1行が長くなりすぎないよう、`決めた基準` は80文字程度に収める。詳細は `playbook.docx` 側にある。
- `※要確認` の項目も行として含め、`決めた基準` に `※要確認` と記載する。
- **法令の下限だけで決まる項目は行にしない**（判断が不要なため）。自社の追加要件がある場合はその部分だけを行にする。

## 4. レビュー依頼の伝え方（観点の明示）

**「全体を確認してください」と依頼してはならない。見てほしい観点を3点程度に絞って提示**する。観点が絞られていないとレビューされない。

観点は次から、その回の作成内容に応じて選ぶ。

| 観点 | 提示する場面 |
|---|---|
| 実績から導いた許容範囲が実務に合っているか | 過去実績を根拠に基準を設定した場合 |
| RED 判定の境界が厳しすぎ／緩すぎないか | 重大度分類を新設・変更した場合 |
| エスカレーション先と金額しきい値が現在の決裁権限と合っているか | §1.2 を設定した場合 |
| `※要確認` の項目（n件）を埋められるか | 未確定項目が残っている場合 |
| 事例から導いた「許容できない条件」が過剰でないか | インシデント事例を反映した場合 |
| 緩和した基準が妥当か | モードBで基準を緩めた場合 |
| 追加した条項が自社の取引実態に合っているか | §2.7 以降を追加した場合 |

依頼文の例（`interaction-format.md` の引用禁止に従い、文書の引用や条番号の参照を含めない）。

> レビューをお願いします。特に次の3点をご確認ください。
> 1. 賠償上限の許容範囲（6〜24ヶ月）が実務に合っているか
> 2. 個人情報の再委託を「受諾不可」としたのが厳しすぎないか
> 3. 未確定の12件を埋められるか

## 5. フィードバックの取り込み

返却されたファイルを `scripts/extract_review_feedback.py` で抽出します。**目視で読み取ってはなりません**（取りこぼしを防ぐため）。

```bash
# Word でレビューされた場合（コメント・変更履歴・表を抽出）
python scripts/extract_review_feedback.py reviewed.docx

# レビューシートで返された場合（.csv / .xlsx のどちらでも可）
python scripts/extract_review_feedback.py review-sheet.csv

# 内容を目で確認したい場合
python scripts/extract_review_feedback.py reviewed.docx --format text
```

標準ライブラリのみで動作し、追加のインストールは不要です。

### 出力の扱い

| 抽出結果 | 意味 | 対応 |
|---|---|---|
| `comments` | Wordコメント（指摘の本文と対象箇所） | 指摘ごとに反映方針を判断する |
| `tracked_changes` の `insertion` / `deletion` | 変更履歴（挿入・削除） | 文言の修正としてそのまま反映を検討する |
| `tracked_changes` の `move_to` / `move_from` | 変更履歴（文字列の移動） | 節の並び替えの指摘として扱う。移動先の位置が既定構成と整合するか確認する |
| `decisions` で `action` が `approved` | 承認 | そのまま確定する |
| `decisions` で `action` が `revise` | 修正指示 | `comment` の内容を反映する |
| `decisions` で `action` が `hold` | 保留 | `※要確認` に戻す |
| `decisions` で `action` が `unanswered` | 未記入 | 追加確認の対象にする |
| `decisions` で `action` が上記以外の文字列 | 想定外の記入（`summary.unrecognized` に計上） | 記入内容を選択フォームで確認する |

### 判断が必要な場合
指摘の意図が読み取れない、または複数の反映方法がある場合は、`interaction-format.md` の選択フォームで確認する。**コメントの文面を引用せず**、論点を平易な言葉で書く。

避ける書き方: 「『SaaS契約では6ヶ月が実態に近い』とのコメントがありました。どうしますか」
推奨する書き方: 「賠償上限の許容範囲の下限を6ヶ月に緩めますか」

---

## 6. 反映と再出力

1. `approved` の項目を確定する。
2. `revise` と Wordコメント・変更履歴の指摘を反映する。
3. `hold` と `unanswered` を `※要確認` として残す。
4. レビュー用ファイル（前回渡したものと同じ形式）を**再出力**する。**承認前の再出力では最終更新日時を据え置き、改訂履歴に行を追加しない**（`playbook-schema.md` §2）。
5. チャットでは「反映した件数、未確定として残した件数」を2文以内で示す。**プレイブック全文や反映内容の一覧をチャット本文に貼らない。**
6. 再レビューを依頼する場合、**前回からの変更点だけを観点として提示**する（全体の再通読を求めない）。
7. `※要確認` が残っていても、法務責任者の承認が得られれば確定してよい。残件は次回改訂の対象として引き渡す。
