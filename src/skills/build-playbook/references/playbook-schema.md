# プレイブックの構成スキーマ

> **このファイルについて:** 生成・改訂するプレイブックのセクション構成と、`review-contract` スキルとの互換要件を定義します。組織の運用に合わせてセクションを**追加**することは可能ですが、既定セクションの番号・意味の変更は互換性を壊します。

## Contents

- 1. なぜ構成を固定するのか
- 2. 既定セクション構成（追加・廃止のルール）
- 3. 各条項節（§2.x）に必ず含める3要素（判定可能性の要件）
- 4. 根拠の記載（5種別・過去実績とインシデント事例の記載要件）
- 5. 匿名化と機密性の要件
- 6. 適切な大きさに保つ（分割の判定は出力時にスキルが行う・単位は契約類型・分割後の構成）

## 1. なぜ構成を固定するのか

`review-contract` スキルは、レビュー指摘のWordコメントに根拠を記載する際、プレイブックの**節番号を引用**します。

```
【重大度】🔴 RED
【指摘理由】損害賠償の上限が設定されておらず、青天井となっている。
【修正の根拠】プレイブック §2.1 に基づき、賠償上限は直近12ヶ月間の委託料相当額を基準とする。
```

節番号が変わると、この根拠参照が実在しない節を指すことになり、レビュー結果の追跡可能性が失われます。したがって**既定セクションの番号は保持**します。

---

## 2. 既定セクション構成

**冒頭にメタデータブロックを置く**（節番号を持たないため、§1〜§6 の番号には影響しない）。

| 項目 | 形式 | 用途 |
|---|---|---|
| 版数 | `1.2` / 承認前は `1.2 (案)` | 版の識別 |
| 最終更新日時 | `YYYY/MM/DD HH:MM` | **改訂時の情報収集の起点**。これ以降のレビュー記録・実績・事例を分析対象とする |
| 承認者 | 役割名（個人名は書かない） | 承認の記録 |
| 承認日 | `YYYY/MM/DD` / 未承認は `未承認` | 承認状態 |
| 次回見直し予定 | `YYYY/MM/DD`（既定は最終更新から1年後） | 定期見直しのトリガー |
| 対象範囲 | 契約類型・立場（例: 業務委託（委託者）、SaaS（顧客）） | 適用範囲の明示 |

```markdown
# 契約書レビュー プレイブック

| 項目 | 内容 |
|---|---|
| 版数 | 1.2 |
| 最終更新日時 | 2026/08/27 16:40 |
| 承認者 | 法務部長 |
| 承認日 | 2026/08/27 |
| 次回見直し予定 | 2027/08/27 |
| 対象範囲 | 業務委託（委託者）、SaaS利用（顧客）、NDA（双方） |
```

**最終更新日時の扱い（改訂の起点の唯一の定義）**
- **エージェントはセッションを越えて状態を保持しないため、最終更新日時はプレイブック本文に記録する**。これが唯一の情報源となる。
- **更新するのは「承認された改訂を確定したとき」だけ**とする。レビュー往復中の再出力、体裁の修正、`※要確認` の一部埋めだけでは更新しない。**未承認の状態で前進させると、次回改訂の収集期間が「前回の実質的な改訂時点」ではなく「前回の再出力時点」になり、その間のレビュー記録や実績を取りこぼす。**
- 承認前の版は、版数に `(案)` を付け、承認日を `未承認` とし、**最終更新日時は前回の承認時のまま据え置く**。
- 改訂時は、この日時以降に発生したレビュー記録・締結実績・インシデント事例を収集対象とする。**この定義を各所で言い換えず、本節を参照する。**
- メタデータブロックが無いプレイブックを読み込んだ場合は、最終更新日時を `※要確認` として扱い、§6 改訂履歴の最新行の日付を代用する。それも無ければ収集期間の起点をユーザーに確認する（既定は直近1年）。

| 節 | タイトル | 必須 | 内容 |
|---|---|---|---|
| 1 | 基本方針 | 必須 | 1.1 自社の立場と優先事項 / 1.2 エスカレーション基準 |
| 2 | 類型別・重要条項のチェックポイント | 必須 | 条項ごとに「自社基準 / 許容できない条件 / フォールバック」 |
| 2.1 | 損害賠償の制限 | 必須 | — |
| 2.2 | 補償 / 損害賠償の範囲 | 必須 | — |
| 2.3 | 知的財産権 | 必須 | — |
| 2.4 | データ保護とセキュリティ | 必須 | — |
| 2.5 | 契約期間と解除・反社条項 | 必須 | — |
| 2.6 | 準拠法と紛争解決 | 必須 | — |
| 2.7以降 | 業種・取引特性による追加条項 | 任意 | **秘密保持、対価・支払条件**、SLA、製造物責任、検査・契約不適合、下請法対応、再委託、監査権、輸出管理、AI・生成物等 |
| 3 | リスクの重大度分類 | 必須 | GREEN / YELLOW / RED の定義・具体例・対応 |
| 4 | 交渉の優先順位 | 必須 | Tier 1（必須要件）/ Tier 2（強く推奨）/ Tier 3（あれば尚可） |
| 5 | 修正案（レッドライン）作成ガイドライン | 必須 | 基本原則と修正案フォーマット |
| 6 | 改訂履歴 | 必須 | 版数・日付・変更概要・承認者。**承認された改訂ごとに1行**とし、最新行の日付をメタデータの最終更新日時と一致させる（日付部分の一致でよい） |

**§2.1〜§2.6 を変更しない理由:** 既に配布済みのプレイブックと `review-contract` のレビュー記録がこの番号を参照しているため、既定6条項の構成は固定します。**秘密保持と対価・支払条件は §2.1〜§2.6 に含まれていませんが、必要な組織では §2.7 以降に追加**します（`interview-guide.md`「§2.7以降 追加条項」で確認）。秘密保持は §2.5 の存続条項、支払条件は下請法対応と重複しやすいため、追加する場合は重複を整理します。

**追加のルール**
- 新しい条項を追加する場合は **§2.7 以降**に採番する。既存の 2.1〜2.6 の間に挿入して番号を繰り下げてはならない。
- 条項を廃止する場合も**番号を再利用せず**、当該節に「（廃止: YYYY/MM/DD、理由）」と残す。過去のレビュー記録が参照している番号を無効にしないため。
- §3 の重大度ラベル（🟢 GREEN / 🟡 YELLOW / 🔴 RED）を組織のリスク分類体系に合わせて変更する場合、`review-contract` スキルの `comment-format.md` が同じラベルでWordコメントを記載するため、**両者を揃える必要がある**。ラベルの変更を提案する際は、この連動が必要である旨をユーザーに伝える。

## 3. 各条項節（§2.x）に必ず含める3要素

| 要素 | 役割 | 記述要件 |
|---|---|---|
| **自社基準** | 目指す条件 | 数値・条件で書く。許容範囲を併記する（例: 直近12ヶ月分。許容範囲: 6〜24ヶ月） |
| **許容できない条件** | RED 判定の境界 | 「これに該当したらエスカレーション」と判定できる形で書く |
| **フォールバック** | 妥協可能な範囲 | 第一希望が拒否された場合に提示できる代替案を書く |

**判定可能性の要件**

レビュー時に機械的に判定できない記述は不可とする。

| 不可 | 可 |
|---|---|
| 「適切な範囲の賠償上限とする」 | 「直近12ヶ月間の委託料相当額。6ヶ月未満は不可」 |
| 「合理的な期間の予告により解約できる」 | 「3ヶ月前の書面通知により解約可能。6ヶ月超は不可」 |
| 「重要な情報は保護する」 | 「個人情報を取り扱う場合、委託先監督条項を必須とする」 |

## 4. 根拠の記載

各基準には根拠を残します。プレイブック本文を読みにくくしないため、**節末に脚注形式でまとめる**ことを既定とします。

```markdown
**自社基準:**
- 賠償上限: 直近12ヶ月間の委託料相当額（許容範囲: 6ヶ月〜24ヶ月）

> **根拠:** 契約審査基準 §4.2（社内規程） / ベンダー契約12件の締結実績（契約管理台帳10件・本文確認2件。6ヶ月:3件、12ヶ月:7件、24ヶ月:2件） / 2026年法務方針ヒアリング
```

根拠の種別は以下の5つに分類し、いずれかを明示します。

| 種別 | 表記例 |
|---|---|
| ヒアリング | `2026年法務方針ヒアリング（法務部長）` |
| 社内規程 | `契約審査基準 §4.2` |
| 過去実績 | `ベンダー契約12件の締結実績（出所: 契約管理台帳。内訳: ...）` |
| インシデント事例 | `情報漏洩事例1件（再委託制限の欠如が原因、影響度: 重大）` |
| 法令 | `下請法第4条第1項` / `個人情報保護法第25条` |

**過去実績の記載要件**
- **件数と出所を必ず併記する**（出所: 契約管理システム / 契約管理台帳 / ファイル添付 / メール）。
- 件数を提示できない情報（口頭で聞いた妥結傾向、メールから受けた定性的な印象）は「過去実績」ではなく**「ヒアリング」として記載**する。根拠の強さを誤認させないため。

**インシデント事例の記載要件**
- **件数と影響度を併記する**。1件でも重大類型（法令違反・情報漏洩・反社リスク・人身損害）であれば、その旨を明記する。
- 事例の内容は原因のレベルまで一般化し、案件が特定できる記述を残さない。

**根拠が無い項目**は値を書かず `※要確認` とする。一般的な商慣行を暫定値とする場合は `※要確認（一般的な商慣行に基づく暫定値）` と併記する。

## 5. 匿名化と機密性の要件

実績から基準を導く際、プレイブックに**取引先名・案件名・個人名を残してはならない**。

| 不可 | 可 |
|---|---|
| 「A商事との案件では6ヶ月で妥結」 | 「ベンダー契約では6ヶ月での妥結実績あり（3件）」 |
| 「山田部長の判断で例外承認」 | 「法務部長判断による例外承認の実績あり」 |
| 「○○プロジェクトでは知財を全面譲渡」 | 「大規模開発委託で知財全面譲渡を受諾した例外あり（1件、要エスカレーション）」 |

インシデント事例は取引先名・案件名・担当者名を含みやすく、かつ社内で機微な扱いを要するため、**原因のレベルまで一般化**する。

| 不可 | 可 |
|---|---|
| 「B社への委託で2025年に個人情報が漏洩した事故」 | 「委託先での個人情報漏洩事例（1件、再委託制限の欠如が原因）」 |
| 「○○案件で下請法違反の指摘を受けた」 | 「委託取引で支払期日に関する行政指摘を受けた事例（1件、影響度: 重大）」 |
| 「C社と賠償額を巡って係争中」 | 「賠償上限の解釈を巡る紛争事例（1件）」 |

**係争中・調査中の事例**は、プレイブックへの反映可否そのものをユーザーに確認する。反映する場合も、案件が特定できる記述は残さない。

プレイブックは組織内で広く共有され、プラグインに同梱されて配布される可能性があるため、匿名化は必須要件とします。

**共有範囲の注意（機密性）**
プレイブックはフォールバック（どこまで譲歩できるか）とエスカレーション基準を含むため、**交渉上の機密**です。§6 で参照者の範囲を確認する際、全社公開や社外共有を選ぶ場合は、フォールバックと Tier 配置が相手方に渡ると交渉上不利になり得る旨を伝え、公開版では当該部分を除くか要約するかを判断させる。

## 6. 適切な大きさに保つ（分割の判断）

プレイブックは**レビュー時に毎回読まれる文書**です。小さすぎれば判断できず、大きすぎれば読まれません。**「削って小さくする」のではなく、必要な基準は書いたうえで、大きくなったら分割します。**

### 大きさの判断

| 状態 | 症状 | 対応 |
|---|---|---|
| **小さすぎる** | 判定に必要な基準が無く `※要確認` が多い、条件分岐に落ちていない | 基準を追加する（削らない） |
| **適切** | 対象範囲の全類型について、条項ごとに3要素が判定可能な形で書かれている | 維持する |
| **大きすぎる** | 条項ごとに類型別の場合分けが並び、レビュー時に自分の類型に該当する記述を探す必要がある | **分割する** |

### 分割の判定（スキルが行う。ユーザーに質問しない）

**判定するのは出力の直前**（`SKILL.md` ステップ6.1）。本文を組み立てて分量が確定してから測ります。**着手前に「分割しますか」と問うてはなりません** — その時点では分量が分からず答えられないうえ、ファイル構成は法務担当者に判断させる事項ではないためです。

**後から分割しても手戻りは生じません。** §2.1〜2.6 の番号は全ファイルで同一、共通部分（§1・§3〜§5）も同一内容のため、分割は出力時のファイル分けに留まります。採番のやり直しやヒアリングの聞き直しは発生しません。

分割したら、**何をどう分けたかを結果として1文で報告**します（例: 「業務委託とSaaSで基準が大きく異なるため、類型ごとに2ファイルに分けて出力しました」）。ユーザーから1つにまとめたい等の希望が出た場合はそれに従います（希望を先に尋ねることはしません）。

### 分割のトリガー（いずれかに該当したら分割する）

- **§2 の条項の過半で、類型ごとの場合分けが3つ以上並んでいる。** レビュー担当者が毎回、自分に関係のない類型の記述を読み飛ばすことになる。
- **全体が通読の実用限界を超えている。** 目安は A4 20ページ（Markdown で概ね1,000行）。1件のレビューでプレイブック全体に目を通せる分量が上限。
- **類型ごとに承認者・改訂サイクルが異なる。** 事業部ごとに運用が分かれている場合、1ファイルでは承認が滞る。

### 分割の単位

**最小単位は契約類型**（業務委託、SaaS、NDA、売買など）。件数の多い類型を単独ファイルにし、件数の少ない類型はまとめて1ファイルにしてよい。

**立場（委託者/受託者、ベンダー/顧客）では分割しない。** 同一類型の中で立場別に書き分ける。立場で分けるとファイル数が倍になり、共通部分の同期コストが釣り合わない。

### 分割後の構成

各ファイルは**自己完結**させる（§1〜§6 のすべてを持つ）。`review-contract` は1回のレビューで1つのプレイブックを読む前提のため、複数ファイルを横断参照させない。

- **ファイル名:** `playbook-<類型>.md`（例: `playbook-業務委託.md`、`playbook-saas.md`）。分割しない場合は `playbook.md`。
- **対象範囲:** メタデータブロックの「対象範囲」に、そのファイルが扱う類型と立場を明記する。**全ファイルを合わせて、扱っている取引形態が漏れなく重複なくカバーされている状態**にする。
- **共通部分（§1 基本方針 / §3 重大度分類 / §4 交渉の優先順位 / §5 修正案ガイドライン）は全ファイルで同一内容にする。** 組織全体の方針であり、類型ごとに変えるものではない。
- **共通部分を改訂したときは、全ファイルに反映する。** 反映漏れの検出は `update-policy.md`「4.6 運用の実効性」で行う。
- 節番号の固定は分割後も同じ（§2.1〜2.6 の番号は変更しない）。類型固有の条項は各ファイルの §2.7 以降に置く。

### 何を書き、何を書かないか

分割の判断とは別に、以下は常に守ります。

| 書くもの | 書かないもの |
|---|---|
| 自社の判断が必要な基準（数値・条件・境界） | 法令の条文・数値（**陳腐化するため**。レビュー時に「e-Gov」法令検索コネクタで取得する） |
| 法令の下限に対する**自社の追加要件**と、法令が適用されるかの**判定条件** | 条項の一般的な意義・背景の説明、契約実務の教科書的な記述 |
| 判定に使う具体例（重大度の例、許容できない条件） | 根拠の全文（実績集計や事例の詳細は別ファイル） |

- **法令要件は「法令の下限を満たすこと」＋適用判定の条件で書く。** 数値を転記しない理由は分量ではなく**法改正で誤りになるため**。ただし適用条件は書く（レビュー時に判定できる必要があるため）。
- **追加する条項は、自社の取引実態と実績・事例に裏付けがあるものに限る。** 「あった方がよい」だけの条項は、判定に使われないまま分量を増やす。
