# 改訂ポリシー

> プレイブックの改訂トリガー、差分提示のフォーマット、出力前チェック、改訂履歴の記録方法。ここに定めた既定値（定期見直しは年1回、改訂候補は3件以上など）は、ヒアリングで組織の運用が確認できた場合はその内容を優先します。

---

## 1. 改訂の基本原則

改訂には2つの起点があり、併用してよい。

| パターン | 起点 |
|---|---|
| **B-1: 規程・方針ドリブン** | 社内規程の改定、法改正、組織変更、事業方針の変更 |
| **B-2: レビュー実績ドリブン** | 蓄積されたレビュー記録・版更新の変更理由の分析（§5） |

収集するインプットの範囲は `evidence-sources.md` §1 に従います。

**「棚卸ししたい」「今の基準で問題ないか確認したい」という依頼もモードBとして受け付ける。** 改訂対象が指定されていなくてよい。**改訂候補が0件なら「改訂不要」と報告して終了してよい**（本文を変更せず、点検した範囲と結果をファイルに残し、次回見直し予定を更新する）。

- **差分を必ず提示する。** ユーザーが変更点を確認せずに確定できる状態にしてはならない。差分の全件はファイルに出力し、承認は影響の大きい節から順にフォームで求める（`interaction-format.md` §6）。
- **削除には理由を付す。** 理由なき削除は行わない。
- **節番号を保持する。** 既定セクション（§1〜§6）の番号・意味は変更しない（`playbook-schema.md` §2）。
- **緩和には根拠を要求する。** 基準を厳しくする改訂より、**緩める改訂の方がリスクが高い**。緩和する場合は根拠（実績・法令・方針変更の承認）を明示し、承認者の確認を得る。
- **一度の改訂で扱う範囲を絞る。** 全面改訂が必要な場合も、セクション単位で提示・承認を得る。

## 2. 改訂トリガー

| トリガー | 検知の手がかり | 主な改訂先 |
|---|---|---|
| **定期見直し** | 「次回見直し予定」を過ぎた | 全体 |
| **法改正** | 参照している法令の改正、新法の施行 | §2.4、§2.5、追加条項 |
| **組織・権限の変更** | 決裁規程の改定、法務体制の変更 | §1.2 |
| **事業方針の変更** | 新規事業、取引形態の追加、海外展開 | §1.1、§2.6、追加条項 |
| **RED判定の頻発** | 同一条件が繰り返し RED になり、都度エスカレーションしている | §2.x、§3 |
| **基準と実績の乖離** | 基準では不可の条件が繰り返し締結されている / 毎回フォールバックで妥結している | §2.x |
| **判定困難の申告** | レビュー担当者が「基準に書かれておらず判断できない」と報告 | §2.x、§3 |
| **交渉の失敗・トラブル** | 契約後に紛争・想定外の負担が発生。事例集・クレーム管理台帳への新規登録 | §2.x、§3、§4 |
| **監査・行政指摘** | 内部監査の所見、行政からの指摘、コンプライアンス報告での指摘 | §2.x、追加条項 |

**【重要】** 「RED判定の頻発」と「基準と実績の乖離」は、**基準が実態に合っていない**シグナルであり、同時に**基準を緩めるべきという結論に直結しない**。過去に不利な条件で締結してしまった結果である可能性があるため、緩和か厳格化かは必ずユーザーに判断させる。

## 3. 差分の提示フォーマット

改訂案は、変更ごとに以下の形式で**ファイルに出力**する。この形式は変更前後の文言を含むため、**チャット本文には貼らない**。チャットでの承認は `interaction-format.md` §5 に従い、変更内容を平易な言葉で1文にしたフォームで求める。

```
【対象】§2.1 損害賠償の制限 / 自社基準
【変更前】賠償上限: 直近12ヶ月間の委託料相当額（許容範囲: 6ヶ月〜24ヶ月）
【変更後】賠償上限: 直近12ヶ月間の委託料相当額（許容範囲: 3ヶ月〜24ヶ月）
【変更理由】小規模なSaaS利用契約では上限3ヶ月が市場標準であり、6ヶ月を主張して交渉が長期化する事例が続いている。
【根拠】SaaS利用契約8件の締結実績（3ヶ月:5件、6ヶ月:3件） / 2026年法務方針ヒアリング（法務部長）
【影響】許容範囲の下限が緩和されるため、従来 YELLOW だった条件の一部が GREEN となる。§3 の具体例も併せて更新が必要。
【区分】緩和
```

- **【区分】** は「新規追加 / 厳格化 / 緩和 / 明確化 / 削除 / 参照更新」のいずれか。
- **【影響】** には他セクションへの波及（§3 の具体例、§4 の Tier 配置、`comment-format.md` のラベル等）を記載する。**波及の確認を省略してはならない。**
- 削除の場合は【変更後】を「（削除）」とし、【変更理由】に削除理由を必ず記載する。新規追加の場合は【変更前】を「（記載なし）」とする。
- 提示は影響範囲の大きい変更（§1 基本方針、§4 優先順位）から始め、条項別基準（§2.x）を番号順に続け、表現の明確化・参照更新は最後にまとめる。

## 4. 出力前チェック（法令適合性・A / B 共通・必須）

**ユーザーに見せる前に、プレイブックが法令に反していないかだけを確認します。** 品質面（曖昧な表現、記載漏れ、節間の矛盾）は出力仕様（`playbook-schema.md`）を満たすように書く時点で担保し、独立したチェックリストは設けません。

**「e-Gov」法令検索コネクタが使える場合に実施する。**

- [ ] 自社基準・許容範囲・フォールバックが、**強行規定の下限を下回っていないか**（下回る場合は法令の下限まで引き上げる。フォールバックとして提示できる範囲にも含めない）。
- [ ] 適用される法令について、**適用判定の条件**がプレイブックに書かれているか（レビュー時に判定できる必要があるため）。
- [ ] 参照している**法令の条番号が現行法と一致**しているか。
- [ ] **法令の条文・数値が本文に転記されていないか**（転記されている場合は「法令の下限を満たすこと」＋適用判定の条件に置き換える。理由は `playbook-schema.md` §6）。

確認する領域は `evidence-sources.md` §3「見落としやすい規制フック」。**モードBでも今回改訂しなかった節を含めて全節を対象にする。**

**コネクタが使えない場合** — 推測で判定してはならない。次の2つを行う。

1. **有効化を促す。** 「法令適合性の確認には e-Gov 法令検索コネクタが必要です。有効化すると、基準が強行規定に反していないかを確認できます」と伝え、有効化して再実行するか、未確認のまま進めるかを承認フォームで確認する。
2. **未確認のまま進める場合** — 法令に関わる基準に `※要確認（条文未確認）` を付し、確認事項の一覧に残す。

### 指摘の報告形式

法令に関わる指摘は**軽微でも承認前にユーザーへ提示する**（他の指摘と異なり、放置すると違法な基準が運用に入るため）。件数が多い場合は一覧をファイルに出力し、チャットには件数と最も重いものを示す。

```
【対象】§2.5 契約期間と解除 / 自社基準
【指摘】支払期日を「検収後90日以内」としているが、下請法の適用取引では法定の上限を超える。
【推奨対応】「法令の下限を満たすこと」に置き換え、適用条件（資本金区分と取引類型）を併記する。
【確認した条文】e-Gov で取得（取得日を記録）
```

## 5. レビュー実績・版更新記録の分析（モードB-2）

対象記録と取得手段は `evidence-sources.md` §2 の ⑥、契約管理システムの制約は同 §4。対象期間の起点はプレイブックの最終更新日時（`playbook-schema.md` §2）。

各記録から「どの条項について」「何を指摘し」「どう決着したか」を条項単位の論点に分解し、同一論点を横断で集約して件数を数える。**1件のレビューが複数論点を含む場合は分けて数える。** 結果は**ファイルに出力**し、チャットには「改訂候補が何件、観測が何件」を1文で示す。

### 改訂候補として扱う件数のしきい値

| 件数 | 扱い |
|---|---|
| **3件以上**（既定） | 改訂候補として差分を提案する |
| **1〜2件** | 「観測」として報告に留め、改訂は提案しない。次回改訂時の継続観察対象とする |
| **1件でも重大** | 法令違反・情報漏洩・反社リスク・人身損害に関わる論点は、1件でも改訂候補として提案する |

しきい値（既定3件）は契約件数の規模によって調整する。年間のレビュー件数が少ない組織では、しきい値を下げるかヒアリングでの補完を前提とする。

### 差分に書く根拠

【根拠】に**レビュー記録の件数と内訳**を記載し、件数と、版更新の変更理由で意図が確認できた件数を分けて書く（例: 「レビュー記録4件（うち変更理由で意図が確認できたもの3件）。指摘内容: 6ヶ月:2件、1年:1件、定めなし:1件」）。

### 禁止事項

- **【禁止】** レビュー記録の多数派を、ユーザーの判断を経ずに新しい基準として確定してはならない。
- **【禁止】** 「基準外で妥結した実績が複数ある」ことのみを根拠に基準を緩和してはならない。**基準が非現実的である可能性と、交渉力・運用に問題がある可能性の両方を併記する。** レビュー記録は「指摘した／しなかった」の記録であり、損害が生じた記録ではないため、緩和を提案する場合はインシデント事例と突き合わせて損害が生じていないことを確認する。
- **【禁止】** 個別のレビュー記録の文面や案件情報をプレイブックに転記してはならない。論点と件数に一般化する。
- **【禁止】** 担当者の判断を、担当者が特定できる形で残してはならない。
- **【禁止】** 係争中・調査中の案件に関する記録を、反映可否をユーザーに確認せずに使用してはならない。

## 6. 改訂履歴の記録（プレイブックの §6）

```markdown
## 6. 改訂履歴

| 版 | 日付 | 変更概要 | 承認者 |
|---|---|---|---|
| 1.1 | 2026/08/27 | §2.1 賠償上限の許容範囲の下限を6ヶ月→3ヶ月に緩和。§3 YELLOW の具体例を更新。 | 法務部長 |
| 1.0 | 2026/04/01 | 初版制定 | 法務部長 |
```

- 承認者は**役割名**で記載する（個人名は残さない）。監査対応で個人単位の承認証跡が必要な場合は、プレイブック本文ではなく承認ワークフローや稟議記録に残す。
- 変更概要には**影響を受けた節番号**を必ず含める。
- **1行 = 1つの承認された改訂**とする。承認前の改訂案は版数に `(案)` を付し、**行を追加しない**（`playbook-schema.md` §2）。
