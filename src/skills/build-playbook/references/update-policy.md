# 改訂ポリシー

> **このファイルについて:** プレイブックの改訂トリガー、差分提示のフォーマット、改訂履歴の記録方法、出力前セルフチェックの項目を定義します。ここに定めた既定値（定期見直しは年1回など）は、ヒアリングで組織の運用が確認できた場合はその内容を優先します。

## Contents

- 1. 改訂の基本原則（B-1 / B-2 の区別・インプットの範囲・改訂候補0件の扱い）
- 2. 改訂トリガー
- 3. 差分の提示フォーマット
- 4. 出力前セルフチェック（品質点検4区分 ＋ 改訂候補の検出2区分）
- 5. レビュー実績・版更新記録の分析（モードB-2）
- 6. 改訂履歴の記録（プレイブックの §6）

## 1. 改訂の基本原則

改訂には2つの起点があり、併用してよい。

| パターン | 起点 | 詳細手順 |
|---|---|---|
| **B-1: 規程・方針ドリブン** | 社内規程の改定、法改正、組織変更、事業方針の変更 | 本ファイル（トリガーと差分フォーマット） |
| **B-2: レビュー実績ドリブン** | 蓄積されたレビュー記録・版更新の変更理由の分析 | 本ファイル「5. レビュー実績・版更新記録の分析」 |

収集するインプットの範囲は `SKILL.md` ステップ3.1（B-1 はモードAと同じ6系統、B-2 は ⑥ を主たる根拠）に従います。

**「棚卸ししたい」「今の基準で問題ないか確認したい」という依頼もモードBとして受け付ける。** 改訂対象が指定されていなくてよく、B-2 の分析と B-1 の陳腐化検出が入口になる。**改訂候補が0件なら「改訂不要」と報告して終了してよい**（本文を変更せず、点検した範囲と結果をファイルに残し、次回見直し予定を更新する）。

以下の原則は両パターンに共通して適用する。

- **差分を必ず提示する。** ユーザーが変更点を確認せずに確定できる状態にしてはならない。差分の全件はファイルに出力し、承認は影響の大きい節から順にフォームで求める（`interaction-format.md`「6. 進行の単位」）。
- **削除には理由を付す。** 現行の記述を削除する場合、削除理由を必ず明示する。理由なき削除は行わない。
- **節番号を保持する。** 既定セクション（§1〜§6）の番号・意味は変更しない。追加は §2.7 以降、廃止は番号を再利用せず注記で残す（`playbook-schema.md`「2. 既定セクション構成」）。
- **緩和には根拠を要求する。** 基準を厳しくする改訂より、**緩める改訂の方がリスクが高い**。緩和する場合は根拠（実績・法令・方針変更の承認）を明示し、承認者の確認を得る。
- **一度の改訂で扱う範囲を絞る。** 全面改訂が必要な場合も、セクション単位で提示・承認を得る。

## 2. 改訂トリガー

以下のいずれかが発生した場合、改訂を検討する。

| トリガー | 検知の手がかり | 主な改訂先 |
|---|---|---|
| **定期見直し** | メタデータブロックの「次回見直し予定」を過ぎた（既定は最終更新から1年後） | 全体 |
| **法改正** | 参照している法令の改正、新法の施行 | §2.4、§2.5、追加条項 |
| **組織・権限の変更** | 決裁規程の改定、法務体制の変更 | §1.2 |
| **事業方針の変更** | 新規事業、取引形態の追加、海外展開 | §1.1、§2.6、追加条項 |
| **RED判定の頻発** | 同一条件が繰り返し RED になり、都度エスカレーションしている | §2.x、§3 |
| **基準と実績の乖離** | 基準では不可の条件が繰り返し締結されている / 毎回フォールバックで妥結している | §2.x |
| **判定困難の申告** | レビュー担当者が「基準に書かれておらず判断できない」と報告 | §2.x、§3 |
| **交渉の失敗・トラブル** | 契約後に紛争・想定外の負担が発生。インシデント事例集・クレーム管理台帳への新規登録 | §2.x、§3、§4 |
| **監査・行政指摘** | 内部監査の所見、行政からの指摘、コンプライアンス報告での指摘 | §2.x、追加条項 |

**【重要】** 「RED判定の頻発」と「基準と実績の乖離」は、**基準が実態に合っていない**シグナルであり、同時に**基準を緩めるべきという結論に直結しない**。過去に不利な条件で締結してしまった結果である可能性があるため、緩和か厳格化かは必ずユーザーに判断させる。

## 3. 差分の提示フォーマット

改訂案は、変更ごとに以下の形式で**ファイルに出力**する。この形式は変更前後の文言を含むため、**チャット本文には貼らない**。チャットでの承認は `interaction-format.md`「5. 質問文の書き方」に従い、変更内容を平易な言葉で1文にしたフォームで求める。

```
【対象】§2.1 損害賠償の制限 / 自社基準
【変更前】賠償上限: 直近12ヶ月間の委託料相当額（許容範囲: 6ヶ月〜24ヶ月）
【変更後】賠償上限: 直近12ヶ月間の委託料相当額（許容範囲: 3ヶ月〜24ヶ月）
【変更理由】小規模なSaaS利用契約では上限3ヶ月が市場標準であり、6ヶ月を主張して交渉が長期化する事例が続いている。
【根拠】SaaS利用契約8件の締結実績（3ヶ月:5件、6ヶ月:3件） / 2026年法務方針ヒアリング（法務部長）
【影響】許容範囲の下限が緩和されるため、従来 YELLOW だった条件の一部が GREEN となる。§3 の具体例も併せて更新が必要。
【区分】緩和
```

- **【区分】** は「新規追加 / 厳格化 / 緩和 / 明確化 / 削除 / 参照更新」のいずれかを記載する。
- **【影響】** には、他セクションへの波及（§3 の具体例、§4 の Tier 配置、`comment-format.md` のラベル等）を記載する。**波及の確認を省略してはならない。**
- 削除の場合は【変更後】を「（削除）」とし、【変更理由】に削除理由を必ず記載する。

### 提示の順序
1. 影響範囲の大きい変更（§1 基本方針、§4 優先順位）から提示する。
2. 次に条項別基準（§2.x）を、条項番号順に提示する。
3. 最後に表現の明確化・参照更新などの軽微な変更をまとめて提示する。

## 4. 出力前セルフチェック

**独立した「診断モード」は設けません。** プレイブックの品質点検は、モードA / モードB のどちらでも**ステップ5.2 の出力前セルフチェックとして必ず実施**します。

区分は6つあり、役割が2種類に分かれます。

| 区分 | 何を見るか | いつ使うか |
|---|---|---|
| 4.1 欠落 | 成果物の品質 | **セルフチェック**（A / B 共通） |
| 4.2 判定不能 | 成果物の品質 | **セルフチェック**（A / B 共通） |
| 4.3 矛盾 | 成果物の品質 | **セルフチェック**（A / B 共通） |
| 4.6 運用の実効性 | 成果物の品質 | **セルフチェック**（A / B 共通） |
| 4.4 陳腐化 | 改訂の必要性 | **B-1 の改訂候補の検出**（`SKILL.md` ステップ7） |
| 4.5 実績・事例との乖離 | 改訂の必要性 | **B-2 の改訂候補の検出**（`SKILL.md` ステップ7・4.3） |

**セルフチェックの範囲と扱い**
- **全節を対象にする。** モードBでも、今回改訂しなかった節を含めて点検する。
- 指摘は**「今回の作成・改訂に起因するもの」と「以前から残っているもの」に分ける**。前者は出力前に自分で修正し、後者は継続課題としてファイルに出力するだけにとどめて承認フローには載せない（改訂の焦点がぼやけるため）。
- 継続課題は `SKILL.md` ステップ7で次回改訂へ引き渡す。

### 4.1 欠落
- [ ] 必須条項（§2.1〜§2.6）すべてに「自社基準 / 許容できない条件 / フォールバック」の3要素が揃っているか。
- [ ] §1.2 のエスカレーション基準に、金額しきい値と承認者（役割名）が定義されているか。
- [ ] §3 の GREEN / YELLOW / RED すべてに定義・具体例・対応が記載されているか。
- [ ] §4 の Tier 1〜3 に項目が割り当てられているか。
- [ ] 主要な取引形態に必要な追加条項（SLA、下請法対応等）が網羅されているか。

### 4.2 判定不能
- [ ] 「適切な」「合理的な」「必要に応じて」等、数値・条件に落ちていない記述がないか。
- [ ] 許容範囲の上限・下限が明示されているか（「12ヶ月程度」のような曖昧な記述になっていないか）。
- [ ] 立場（委託者 / 受託者等）によって基準が変わる条項で、立場別の記述が分かれているか。

### 4.3 矛盾
- [ ] §2.x の許容範囲と §3 の重大度の具体例が整合しているか。
- [ ] §2.x の「許容できない条件」と §4 の Tier 配置が整合しているか（Tier 1 の項目が §2 で許容されていないか）。
- [ ] §1.2 のエスカレーション基準と各 §2.x の RED 条件が整合しているか。
- [ ] フォールバックが「許容できない条件」の範囲に踏み込んでいないか。

### 4.4 陳腐化
- [ ] 参照している法令の条番号が現行法と一致しているか（「e-Gov」法令検索コネクタで確認）。**コネクタが使えない場合は「条文未確認」として指摘に残し、推測で判定しない。**
- [ ] 法改正により必須となった要件が反映されているか。
- [ ] 法令の条文や数値がプレイブック本文に転記されていないか（転記されている場合は「法令の下限を満たすこと」＋適用判定の条件に置き換える。理由は `playbook-schema.md`「6. 適切な大きさに保つ」）。
- [ ] 改訂履歴（§6）の最終更新から1年以上経過していないか。
- [ ] 廃止した条項の注記が残っているか（番号の再利用が起きていないか）。

### 4.5 実績・事例との乖離
- [ ] 基準では「許容できない条件」に該当する条件で締結されている契約がないか。
- [ ] 毎回フォールバックで妥結している条項がないか（自社基準が実態に合っていない可能性）。
- [ ] 実績が存在しない条項の基準が、根拠なく設定されていないか。
- [ ] 前回改訂後に発生したインシデント・トラブル事例が、基準に反映されているか。
- [ ] 事例の原因となった条件が、いまも「許容範囲」または「フォールバック」に含まれていないか。
- [ ] 監査・行政指摘を受けた項目が、§2.x または追加条項に反映されているか。
- [ ] 根拠に「過去実績」と記載された項目に、**件数と出所が併記**されているか（件数のない情報が実績として扱われていないか）。

### 4.6 運用の実効性
- [ ] 冒頭にメタデータブロックがあり、版数・最終更新日時・承認者・承認日・次回見直し予定・対象範囲が埋まっているか。
- [ ] **承認済みの版**について、メタデータの最終更新日時の日付部分と §6 改訂履歴の最新行の日付が一致しているか（承認前の版は据え置きのため対象外）。
- [ ] 改訂履歴の行が、承認された改訂ごとに1行になっているか（往復で増殖していないか）。
- [ ] `review-contract` が参照する節番号（§2.1 等）が既定構成と一致しているか。
- [ ] 取引先名・案件名・個人名が残っていないか（`playbook-schema.md`「5. 匿名化と機密性の要件」）。
- [ ] **大きさが適切か。** 条項ごとに類型別の場合分けが3つ以上並んでいないか、全体が通読の実用限界（目安 A4 20ページ / 概ね1,000行）を超えていないか。超えている場合は**分割を提案**する（`playbook-schema.md`「6. 適切な大きさに保つ」）。
- [ ] **小さすぎないか。** 対象範囲の類型について、条項ごとの3要素が判定可能な形で埋まっているか（`※要確認` が多い場合は基準の確定が必要で、削るのではなく追加する）。
- [ ] 法令の条文・数値が転記されていないか（陳腐化するため。「法令の下限を満たすこと」＋適用判定の条件に置き換える）。
- [ ] 判定に使わない記述（条項の一般的な意義、契約実務の解説）が増えていないか。
- [ ] **分割している場合:** 共通部分（§1・§3〜§5）が全ファイルで同一か。対象範囲が全ファイルを合わせて漏れなく重複なくカバーされているか。ファイル名と「対象範囲」の記載が一致しているか。
- [ ] `※要確認` が残置されたまま長期間放置されていないか。
- [ ] 承認者・承認日が記録されているか。

### セルフチェック結果の報告形式

指摘は以下の形式で**ファイルに出力**する。チャット本文には「今回起因で修正した件数」と「継続課題として残した件数」のみを示す。

**`【由来】` に「今回」「既存」を必ず記載する。** 「今回」は出力前に自分で修正し、修正できない場合のみ承認前にユーザーへ提示する。「既存」は継続課題としてファイルに残すだけで、承認フォームには載せない。

```
【区分】判定不能
【由来】既存（前回改訂より前から残っている）
【対象】§2.4 データ保護とセキュリティ / 自社基準
【指摘】「漏洩事故は速やかに報告させる」とあり、報告期限が数値化されていないため、レビュー時に逸脱の判定ができない。
【推奨対応】報告期限を時間単位で定義する（例: 発覚後24時間以内、許容範囲48時間）。
【優先度】高
```

**優先度の基準:** 高 = レビューの判定に支障がある / 中 = 判定できるが解釈の幅が残る / 低 = 表現の改善に留まる。

## 5. レビュー実績・版更新記録の分析（モードB-2）

**モードB-2 の分析手順です。** 契約管理システムに蓄積された過去のレビュー記録と版更新時の変更理由から、「明文化されていないが実務で判断している論点」と「明文化されているが守られていない基準」を検出します。

### 5.1 分析対象の記録

| 記録 | 得られる情報 | 取得手段 |
|---|---|---|
| **レビュータスク** | レビューの対象・時期・担当、完了状況 | 「ContractS CLM」MCP の `list_task` |
| **レビュータスクのコメント** | レビュー依頼の背景、交渉経緯、社内の懸念、レビュー完了コメント（指摘の要点・修正箇所の概要） | `list_comment`（`resource_type="TASK"`、`resource_id` にタスクID） |
| **タスクコメントの添付資料** | 相手方からの修正依頼、交渉経緯資料 | `list_comment` のレスポンスの `attachmentFiles` → `download_attachment` |
| **版更新の変更理由** | レビュー前からの変更意図と要点、主要な修正箇所の意図、**ユーザーが最終的に加えた変更・判断** | 契約管理システムのバージョン履歴（下記「取得できない場合」を参照） |
| **契約本文（版間の差分）** | 実際に反映された文言、最終的に締結された条件 | `download_document`（版を指定できる場合は各版） |

**版更新の変更理由について:** `review-contract` スキルは版更新時に、レビューの目的・主要な修正箇所とその意図・ユーザーが最終的に加えた判断を4,000文字以内でまとめた更新コメントを登録します。これが B-2 の最も情報量の多い入力です。

**取得できない場合:** 接続中のコネクタにバージョン履歴・更新コメントを読み出す手段が無い場合は、**同じ内容が `post_task_comment` で投稿されたレビュー完了コメントに残っている**ため、`list_comment` から取得する。両方が取得できない場合は、レビュー担当者へのヒアリングで代替し、根拠種別は「ヒアリング」として記録する（件数の裏付けがないため）。

---

### 5.2 収集フロー

1. **対象期間の決定:** **プレイブックの最終更新日時を起点**とする（定義と代替手順は `playbook-schema.md`「2. 最終更新日時の扱い」。本ファイルでは言い換えない）。
2. **タスクの一覧取得:** `list_task` で対象期間の完了済みレビュータスクを取得する。件数が多い場合は契約類型・自社の立場で絞り込む。
3. **記録の取得:** 各タスクについて `list_comment`（`resource_type="TASK"`、`resource_id` にタスクID）でコメントを取得する。`attachmentFiles` があれば `download_attachment` で資料を取得する。
4. **変更理由の取得:** 版更新の変更理由を取得する（取得手段が無い場合は手順3のレビュー完了コメントで代替）。
5. **論点への分解:** 各記録から「どの条項について」「何を指摘し」「どう決着したか」を抽出し、**条項単位の論点**に分解する。1件のレビューが複数論点を含む場合は分けて数える。
6. **論点の集約:** 同一論点を横断で集約し、出現件数を数える。
7. **観測パターンの分類:** 「4. 観測パターンと改訂の示唆」の表に従って各論点を分類する。
8. **匿名化:** 取引先名・案件名・担当者名を除去する（`playbook-schema.md`「5. 匿名化の要件」）。

### 5.3 観測パターンと改訂の示唆

| 観測パターン | 示唆 | 反映先 |
|---|---|---|
| プレイブックに無い論点の指摘が繰り返されている | **ルールの欠落**。実務では判断しているが基準が明文化されていない | §2.x に基準を新設、または §2.7 以降に条項を追加 |
| ほぼ同じ修正文言が繰り返し使われている | 標準文言として登録できる | §5 に標準文言・修正案の例として追加 |
| 指摘したが相手方に受諾されず、基準外の条件で妥結している | 基準が実態と乖離、または交渉の優先度が低い | 許容範囲・フォールバックの見直し（**緩和には根拠が必要**）、または §4 Tier の引き上げ |
| レビュー担当がプレイブックと異なる判断をしている | 基準が不明確または陳腐化している | 判定条件を数値・条件で明確化 |
| ユーザーが最終判断でレビュー指摘を取り消している | 基準が過剰、または指摘の根拠が弱い | 基準の妥当性を再検討。取消理由を確認する |
| RED 判定がエスカレーションされずに妥結している | エスカレーション運用が機能していない、または RED 分類が過剰 | §1.2 の実効性を確認、§3 の分類を見直し |
| 同一条件が毎回 YELLOW → フォールバックで妥結している | 自社基準が非現実的 | 自社基準そのものを見直し（フォールバックを自社基準に格上げするか判断） |
| 変更理由に「相手方要求により元の条件に戻した」記録が多い | Tier 配置が実態と合っていない | §4 の Tier を見直し |
| 特定条項でレビュー時間・往復回数が突出している | 基準が曖昧で判断に迷っている | 判定条件の明確化、標準文言の整備 |

**【重要】** これらは**改訂の候補を示すシグナル**であり、改訂内容そのものではありません。特に「基準外で妥結している」「指摘が取り消されている」は、**基準を緩めるべき根拠にも、交渉力・運用を改善すべき根拠にもなり得ます**。どちらとして扱うかは必ずユーザーに判断させる。

---

### 5.4 改訂候補の判定（件数のしきい値）

| 件数 | 扱い |
|---|---|
| **3件以上**（既定） | 改訂候補として差分を提案する |
| **1〜2件** | 「観測」として報告に留め、改訂は提案しない。次回改訂時の継続観察対象とする |
| **1件でも重大** | 法令違反・情報漏洩・反社リスク・人身損害に関わる論点は、1件でも改訂候補として提案する |

しきい値（既定3件）は契約件数の規模によって調整する。年間のレビュー件数が少ない組織では、しきい値を下げるかヒアリングでの補完を前提とする。

---

### 5.5 差分への反映

改訂案は `update-policy.md`「3. 差分の提示フォーマット」に従い**ファイルに出力**する。B-2 では【根拠】に**レビュー記録の件数と内訳**を記載する。チャットでの承認は、レビュー記録の文面を引用せず、論点と件数を平易な言葉で示したフォームで求める（`interaction-format.md`「5. 質問文の書き方」）。

```
【対象】§2.4 データ保護とセキュリティ / 自社基準
【変更前】（記載なし）
【変更後】アクセスログの保存期間: 1年以上を要求する（許容範囲: 6ヶ月まで）
【変更理由】直近1年のレビュー記録で、アクセスログの保存期間について4件の指摘があり、いずれも担当者の判断で個別に条件を設定していた。基準が未整備のため判断がばらついている。
【根拠】レビュー記録4件（うち版更新の変更理由で意図が確認できたもの3件）。指摘内容: 6ヶ月:2件、1年:1件、期間の定めなし:1件
【影響】新規の基準追加。§3 の YELLOW 具体例に「保存期間が6ヶ月未満」を追加する必要がある。
【区分】新規追加
```

**根拠の記載要件**
- 件数と、版更新の変更理由で意図が確認できた件数を分けて記載する。
- レビュー記録は「指摘した／しなかった」の記録であり、**損害が生じた記録ではない**。緩和方向の改訂を提案する場合は、`evidence-sources.md`「4. インシデント・トラブル事例からの抽出」で収集した事例と突き合わせ、その条件で損害が生じていないことを確認する。

---

### 5.6 禁止事項

- **【禁止】** レビュー記録の多数派を、ユーザーの判断を経ずに新しい基準として確定してはならない。
- **【禁止】** 「基準外で妥結した実績が複数ある」ことのみを根拠に基準を緩和してはならない。交渉力・運用の問題である可能性を必ず併記する。
- **【禁止】** 個別のレビュー記録の文面や案件情報をプレイブックに転記してはならない。論点と件数に一般化する。
- **【禁止】** 版更新の変更理由に含まれる担当者の判断を、担当者が特定できる形で残してはならない。
- **【禁止】** 係争中・調査中の案件に関する記録を、反映可否をユーザーに確認せずに使用してはならない。

## 6. 改訂履歴の記録（プレイブックの §6）

改訂したプレイブックには、改訂履歴を記録する。

```markdown
## 6. 改訂履歴

| 版 | 日付 | 変更概要 | 承認者 |
|---|---|---|---|
| 1.1 | 2026/08/27 | §2.1 賠償上限の許容範囲の下限を6ヶ月→3ヶ月に緩和。§3 YELLOW の具体例を更新。 | 法務部長 |
| 1.0 | 2026/04/01 | 初版制定 | 法務部長 |
```

- 承認者は**役割名**で記載する（個人名は残さない）。監査対応で個人単位の承認証跡が必要な場合は、プレイブック本文ではなく承認ワークフローや稟議記録に残す（プレイブックは広く共有される文書のため）。
- 承認前の改訂案は、版数に `(案)` を付す（例: `1.2 (案)`）。**承認前の版では改訂履歴に行を追加しない。**
- 変更概要には**影響を受けた節番号**を必ず含める。
- **1行 = 1つの承認された改訂**とする。レビュー往復で再出力しても行を増やさない。
- メタデータの最終更新日時との関係は `playbook-schema.md`「2. 最終更新日時の扱い」に従う（本ファイルでは言い換えない）。
