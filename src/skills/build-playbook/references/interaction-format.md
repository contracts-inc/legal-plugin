# 対話フォーマット

> **このファイルについて:** ユーザーへの質問・判断依頼をすべてフォーム形式に統一するための規約です。回答負荷を下げ、出力量を抑えることを目的とします。本ファイルの形式は厳守してください。

## Contents

- 原則
- 1. 選択フォーム（基本形）
- 2. 数値入力の扱い
- 3. 承認フォーム（次のステップに進む場合）
- 4. 一括フォーム（ファイルを渡して記入してもらう場合）
- 5. 質問文の書き方（自己完結の原則）
- 6. 進行の単位（1つずつ完結させる）
- 7. 出力量の制限
- 8. 禁止事項

---

## 原則

1. **質問はすべてフォーム形式にする。** 番号で答えられる選択肢を用意する。関連する項目は**1つのフォームにまとめて提示してよい**。
2. **質問文だけで何を聞かれているか分かるようにする。** 文書の引用・出典参照を質問に含めない（詳細は「5. 質問文の書き方」）。
3. **次に何をするかをユーザーに選ばせない。** スキルが次の1手を決めて宣言し、承認だけを求める。
4. **長い一覧はファイルに出す。** チャット本文にはフォームと短い背景のみを置く。

## 1. 選択フォーム（基本形）

ユーザーに基準や方針を決めてもらう場合は、必ずこの形式を使う。関連する項目はまとめてよい。

```
## 損害賠償の制限について（3問）

過去のベンダー契約12件では、賠償上限は6〜24ヶ月に分布しています（12ヶ月が7件）。

**Q1. 賠償上限の算定基礎をどれにしますか**
1. 直近12ヶ月の対価（推奨: 実績で最多）
2. 直近6ヶ月の対価
3. 契約総額
4. 定額（金額をご記入ください）
5. 上限を設けない
6. 保留（後で決める）

**Q2. これ未満は受諾しないという下限はどこですか**
1. 12ヶ月
2. 6ヶ月
3. 3ヶ月
4. 下限を定めない
5. 保留（後で決める）

**Q3. 上限は双方に適用しますか**
1. 双方に適用する（推奨）
2. 相手方のみに適用でも可
3. 自社が賠償を受ける場合のみ上限を要求する
4. 保留（後で決める）

番号でお答えください（例: Q1=1, Q2=2, Q3=1）。
```

### ルール
- **1フォームあたりの設問は7問まで。** これを超える場合は設問を分けるか、「4. 一括フォーム」でファイルを渡す。
- **1フォームにまとめてよい範囲は、同一セクション・同一契約類型・同一立場の項目に限る。** 異なるセクションや異なる立場の質問を同じフォームに混ぜない。
- **見出しに対象と問数を書く。**「損害賠償の制限について（3問）」のように、何についての質問が何問あるかを示す。
- **背景は2文以内。** 判断材料（実績の件数、事例の件数、法令の下限）を数値で短く添える。長い根拠はファイルに出す。
- **単一選択の設問は選択肢6つ以内**（「保留」を含めて7つ以内）。超える場合は設問を分ける。
  - **複数選択のチェックリスト形式はこの上限の対象外**（取引形態の棚卸し、除外事由の列挙、追加条項の候補など、網羅的に挙げること自体に意味がある設問）。この場合は「複数選択可。番号をカンマ区切りで記入」と明記し、記入例を添える。
- **推奨または既定を1つ明示する。** 根拠は「実績で最多」「法令の下限」など短く添える。推奨できない場合は付けない。
- **各設問に「保留（後で決める）」を必ず置く。** 選ばれた項目は `※要確認` として記録し、先に進む。
- **回答方法を1行で示す。** 記入例を添える。

## 2. 数値入力の扱い

金額のしきい値・期間・率など、選択肢で表しきれない値は、**選択肢の1つとして記入欄を用意**する。自由記述だけで聞いてはならない。

```
**Q. 上位者の承認が必要になる契約金額はいくら以上ですか**
1. 1,000万円以上
2. 5,000万円以上
3. 1億円以上
4. 上記以外（金額をご記入ください。例: 3,000万円）
5. 金額では区切っていない
6. 保留（後で決める）
```

段階が複数ある場合（1,000万円で部長、5,000万円で役員など）は、段階ごとに問いを分ける。

## 3. 承認フォーム（次のステップに進む場合）

工程を進める、改訂を確定する、外部システムに登録する場合に使う。**「次に何をしますか」と尋ねてはならない。**

```
## 次の工程に進みます

基本方針が確定しました。次に損害賠償・補償・知的財産など6つの条項について基準を決めます。

1. このまま進める
2. 基本方針を修正したい（修正内容をご記入ください）
3. ここで中断する（作成済みの内容をファイルで出力します）

番号でお答えください。
```

### ルール
- **次に行うことを1文で宣言する。** 選択肢は「進める / 修正する / 中断する」の3つを基本とし、これ以上に増やさない。
- **その操作で何が変わるかを明示する。** 特に外部システムへの登録・上書き・共有では、対象と影響範囲を1文で書く。
- 承認を得ずに、出力・共有・登録・タスク操作へ進んではならない。

## 4. 一括フォーム（ファイルを渡して記入してもらう場合）

### 使用条件

**モードA（新規構築）は原則として一括フォームを配布します。** 新規構築の確認事項は共通だけで100問を超えるため、選択フォームで逐次確認すると往復が過大になります。

**モードB（更新・改訂）は原則として選択フォームで逐次確認します。** 改訂対象に絞られており、確認事項が少ないためです。ただし以下に該当する場合はモードBでも一括フォームを配布します。

- 未確定の確認事項が **20件以上** ある。
- ユーザーが「まとめて答えたい」「一覧で欲しい」と述べた。
- 複数の担当者（法務・事業・情報セキュリティ）に分担して回答してもらう必要がある。
- ユーザーが回答を保留し、後日まとめて回答したいと述べた。

### 一括フォームと逐次確認の関係

**一括フォームを配布しても、逐次確認は無くなりません。** 以下は配布後に選択フォームで確認します。

| 対象 | 理由 |
|---|---|
| 記入内容に矛盾・欠落がある項目 | 記入だけでは解決しない |
| 判断が重い項目（RED判定の境界、エスカレーション先、基準の緩和） | 判断材料の提示が必要 |
| 実績・事例を踏まえた判断が必要な項目 | 件数などの背景を添えて聞く必要がある |
| 追加条項のスコープ確定 | 後続の質問セットが変わる |

**進行の単位（「6. 進行の単位」）は、この逐次確認と、モードBの差分確認に適用されます。** 一括フォームの配布はセクション順の進行を置き換えるものではなく、回答を先に集めておく手段です。

### 手順
1. `assets/interview-form.md` を土台に、**該当する項目だけを抜き出した記入用ファイル**を生成する。該当しない契約類型・規制のセクションは追加しない。類型別セクションの転記方法は同ファイル「転記の手順」に従う。
2. 立場によって基準が変わる場合は、**立場ごとに別のフォーム**を配布する（同ファイル「立場が分かれる場合」）。
3. ファイルを出力し、チャット本文には次の2文のみを書く。
   - 何件の確認事項を含むか。
   - どこを埋めればよいか（`[ ]` に番号または数値を記入する、わからない項目は「保留」と書く）。
4. 記入済みファイルを受領したら、**回答内容の要約を提示せずに**そのまま基準へ反映する。要約の提示は出力量を増やすだけで確認の役に立たない。
5. 未記入・「保留」の項目は `※要確認` として記録し、確認事項の一覧に残す。
6. 上記「一括フォームと逐次確認の関係」に該当する項目を、選択フォームで確認する。

### ファイル配布と対話の使い分け
| 状況 | 方法 |
|---|---|
| モードA（新規構築） | 一括フォームをファイルで配布し、その後に逐次確認 |
| モードB で確認事項が19件以下 | 選択フォームでまとめて提示（1フォーム7問まで） |
| モードB で確認事項が20件以上 | 一括フォームをファイルで配布 |
| 一括フォームの回答に矛盾・欠落がある | 該当項目のみ選択フォームで確認 |
| 判断が重い項目（RED判定の境界、エスカレーション先、基準の緩和） | 他の項目と混ぜず、単独のフォームで確認 |

## 5. 質問文の書き方（自己完結の原則）

**チャット上では引用元をたどれないため、質問は引用なしで成立させる。** ユーザーが別の文書やチャットの過去ログを見返さなくても、質問文だけで何を聞かれているか分かる状態にする。

### 質問に含めてはならないもの
- 現行プレイブック・社内規程・契約書・雛形の**条文や記述の引用**
- レビュー記録・タスクコメント・メールの**文面の引用**
- 法令の**条文の引用**
- 出典の参照（規程名と条番号、事例の識別子、ファイル名、節番号だけを示して内容を書かない参照）
- 「上記の」「先ほどの」「以下の記述について」など、**別の箇所を見ないと分からない指示語**

### 代わりに書くもの
- 何を決めるのかを、平易な言葉で1文にする。
- 現状に触れる必要がある場合は、引用ではなく**内容を言い換えた事実**を1文で書く（例: 「現在は報告期限を『速やかに』としており、時間の定めがありません」）。
- 判断材料は**数値と件数だけ**を示す（例: 「過去12件中7件が12ヶ月です」「同じ指摘が4件ありました」）。文書名・条番号は書かない。
- 根拠（出典）は質問に書かず、**プレイブック本文の根拠注記とファイル側の記録に残す**。

### 例

| 避ける書き方 | 推奨する書き方 |
|---|---|
| 「契約審査基準 §4.2 に『賠償上限は年間委託料の12ヶ月分を上限とする』とありますが、これを維持しますか」 | 「賠償上限を『直近12ヶ月の対価』とします。よろしいですか」 |
| 「現行プレイブック §2.4 の以下の記述を変更しますか: 『漏洩事故は速やかに報告させる』」 | 「漏洩事故の報告期限は現在、時間の定めがありません。何時間以内としますか」 |
| 「レビュー記録に『相手方要求により元の条件に戻した』との記載が4件あります。§4 の Tier を見直しますか」 | 「中途解約権は、交渉しても4件で相手方の条件のまま妥結しています。必須条件から外しますか」 |
| 「下請法第4条第1項第2号の規定に照らして支払期日を確認してください」 | 「支払期日は法令上、受領後60日以内である必要があります。自社基準を60日以内としてよいですか」 |
| 「上記の実績分布を踏まえてご判断ください」 | 「過去12件中7件が12ヶ月です。12ヶ月を自社基準としてよいですか」 |

### 改訂（モードB）の差分を確認する場合
差分の全文（変更前・変更後の文言を含む）は**ファイルに出力**し、チャットの承認フォームでは**変更の内容を平易な言葉で1文**にする。

```
## 改訂案の確認（3件）

**Q1. 賠償上限の許容範囲の下限を、6ヶ月から3ヶ月に緩めますか**
過去8件のSaaS利用契約のうち5件は3ヶ月で妥結しており、6ヶ月を主張すると交渉が長期化しています。
1. 緩める（下限を3ヶ月にする）
2. 現状のまま（下限は6ヶ月）
3. 別の値にする（値をご記入ください）
4. 保留（後で決める）
```

## 6. 進行の単位（1つずつ完結させる）

**まとめて進めず、単位ごとに確定させてから次に進む。**

### セクションの順序
基本方針 → 損害賠償 → 補償 → 知的財産 → データ保護 → 契約期間・解除 → 準拠法・紛争解決 → 追加条項 → 重大度分類 → 交渉の優先順位 → 修正案の方針 → 運用・改訂

前のセクションを確定してから次に進む。異なるセクションの質問を同じフォームに混ぜてはならない。

### 契約類型が複数ある場合
1. 棚卸しした類型を、**件数の多い順**に並べる。
2. **1類型ずつ完結させる。** 1つ目の類型について条項別基準と追加条項を確定し、承認フォームで次の類型に進む。
3. 2つ目以降の類型では、確定済みの内容と**同じでよい項目を明示**し、異なる項目だけを質問する（例: 「賠償上限は業務委託と同じ12ヶ月でよいですか」）。

### 立場が分かれる場合
委託者/受託者、ベンダー/顧客のように立場で基準が変わる場合は、**立場ごとに分けて完結させる**。1つのフォームに両方の立場を混ぜない。

### プレイブックを分割する場合
判断基準と分割後の構成は `playbook-schema.md`「6. 適切な大きさに保つ」に従う（本ファイルでは言い換えない）。進行の観点では次を守る。

- **分割の可否をユーザーに質問しない。** 出力時に分量を測ってスキルが判定し、結果を1文で報告する（`SKILL.md` ステップ6.1）。着手前に問うと、分量が未確定で答えられないうえ、ファイル構成という技術的判断を法務担当者に求めることになる。
- **ヒアリングは分割の有無に関係なく、類型ごとに1つずつ完結させる。** 件数の多い類型から順に進め、2つ目以降は確定済みと同じでよい項目を明示して差分だけを聞く。この進め方は、最終的に1ファイルになるか複数になるかとは独立している。
- 分割して出力した場合、**共通部分（§1・§3〜§5）は全ファイルで同一**にする。

### モードBの差分確認
差分の全件はファイルに出したうえで、**影響の大きい節から順に**承認フォームで確認する。1フォームあたり3件程度までにまとめ、全件を一度に提示しない。

### 進捗の提示
フォームの見出しに対象と問数（「損害賠償の制限について（3問）」）を、工程の切り替わりでは残りの工程数（「残り6条項」）を示す。ユーザーが残量を把握できる状態を保つ。

## 7. 出力量の制限

### チャット本文に置くもの
- フォーム（1件）
- 背景・判断材料（2文以内）
- 直前の回答の反映結果（1文。「賠償上限を12ヶ月として記録しました」程度）

### ファイルに出すもの
| 内容 | 理由 |
|---|---|
| 実績レンジの集計結果（条項別の一覧） | 件数・内訳を含むと長大になる |
| インシデント事例の整理結果 | 事例ごとの原因と反映先の対応表 |
| レビュー実績の分析結果（観測パターン別の論点一覧） | 論点数が多い |
| セルフチェックで残った継続課題 | 指摘が多数になる |
| 差分の全件（モードB） | 変更前・変更後の文言を含むため長い |
| 確認事項（`※要確認`）の一覧 | 項目数が多い |
| プレイブック本文 | 常にファイル |

### 禁止
- 分析結果・集計結果の全文をチャット本文に貼らない。
- 1ターンに複数の表を出さない（フォームを除く）。
- 確定した内容を繰り返し要約しない。

## 8. 禁止事項

- **【禁止】** フォーム形式以外で質問すること（自由記述での回答を必須にすること）。数値・固有名詞の記入を求める場合も、選択肢の1つとして記入欄を提示する。
- **【禁止】** 質問に文書の引用・条文・出典参照・「上記の」等の指示語を含めること。**この禁止は質問文と背景に適用される。** 一括フォームや成果物の構造見出し（「§2.1 損害賠償の制限」など）は、どこを記入しているかを示す目印であり対象外。
- **【禁止】** 1フォームに8問以上を詰め込むこと（設問を分けるか、一括フォームをファイルで渡す）。
- **【禁止】** 単一選択の設問に7つ以上の選択肢を並べること（複数選択のチェックリストは対象外）。
- **【禁止】** 異なるセクション・異なる契約類型・異なる立場の質問を1つのフォームに混ぜること。
- **【禁止】** 一括フォームを配布したことを理由に、矛盾・欠落・重い判断の逐次確認を省略すること。
- **【禁止】** 「次に何をしますか」「どちらから進めますか」のように、次の行動の選択をユーザーに委ねること。
- **【禁止】** 選択肢に「保留」を用意しないこと。
- **【禁止】** 差分・セルフチェック結果・集計結果を一括でチャット本文に提示すること。
- **【禁止】** プラグインの構成・ファイルパス・ビルド手順を選択肢として提示すること（`SKILL.md` の基本原則を参照）。
- **【禁止】** **プレイブックのファイル構成・分割の有無を質問すること。** 分量が確定していない段階では答えられず、技術的判断を法務担当者に求めることになる。分割は出力時にスキルが判定し、結果を報告する。
