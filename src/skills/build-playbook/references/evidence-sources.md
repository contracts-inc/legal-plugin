# 根拠情報の収集フロー

> **このファイルについて:** プレイブックの基準を裏付ける根拠情報の収集手順を定義します。利用可能な情報源だけを使い、使えない系統を推測で補完しないことが原則です。手順本体は特定製品に依存しない形で記述し、ContractS CLM 利用時の具体的なツール操作は該当箇所に具体例として併記しています。

## Contents

- 0. 事前に用意すると良いインプット（モードA・B-1、初回向け）
- 収集する6系統（優先順位・矛盾時の扱い）
- 1. ヒアリング
- 2. 社内規程・既存基準書・契約書雛形（雛形からの抽出観点）
- 3. 過去契約・交渉実績からの抽出（取得経路・集計項目・禁止事項）
- 4. インシデント・トラブル事例からの抽出（対象・取得経路・基準への変換）
- 5. 法令・強行規定
- 6. 情報源が得られない場合

## 0. 事前に用意すると良いインプット（モードA・B-1、初回向け）

**利用者はプレイブックを作った経験がないことが多いため、何を渡せばよいかを先に示します。** 以下をそのまま提示してよい（`SKILL.md` ステップ1.2）。

**モードB-1（規程・方針ドリブンの改訂）でも、モードAと同じインプットを受け付けます。** 改定された規程だけに絞らず、以下すべてを収集対象とします。改訂内容の妥当性は規程の改定以外の材料でも裏付ける必要があるためです。

| 用意するもの | どこにあるか | あると何が良くなるか | 無い場合 |
|---|---|---|---|
| **契約審査基準・契約管理規程** | 法務部門の規程集、社内ポータル | 既に承認済みの基準をそのまま使えるため、決め直しが不要になる | ヒアリングで一から決める |
| **自社の契約書雛形（テンプレート）** | 法務部門、共有フォルダ、契約管理システムのテンプレート、Google Drive / SharePoint | **どの契約類型を扱っているかが分かり、質問すべき類型を特定できる**。雛形の条項が事実上の自社基準になっているため、基準の初期値として使える | 取引形態をヒアリングで棚卸しし、基準を一から決める |
| **決裁規程・職務権限規程** | 総務・経営企画部門 | エスカレーションの金額しきい値と承認者が確定する | 承認者が決まらず `※要確認` が残る |
| **過去の契約書（主要な取引形態ごとに5〜10件）** | 契約管理システム、共有フォルダ | 実際に妥結した条件から許容範囲とフォールバックを裏付けられる | 許容範囲が推測できず `※要確認` になる |
| **契約管理台帳（Excel等）** | 法務・購買部門 | 賠償上限や契約期間が列で入っていれば、契約書を開かずに集計できる | 契約書を個別に確認するか、ヒアリングで代替 |
| **トラブル事例集・インシデント台帳** | 法務、リスク管理、内部監査部門 | 「許容できない条件」とRED判定の根拠になる。最も価値が高い | ヒアリングで過去のトラブルを聴取 |
| **情報セキュリティ規程・個人情報保護規程** | 情報システム、法務部門 | データ保護条項の基準が確定する | ヒアリングで決める |
| **過去のレビューメモ・法務の指摘集** | 法務担当者の手元、メール | 繰り返し指摘している論点を基準に格上げできる | 検出できない |

### 伝え方のルール
- **すべて任意である**ことを明示する。1つも無くてもヒアリングだけで作成できる。
- **優先順位を示す。** 揃えるのが難しい場合は「決裁規程」と「トラブル事例集」の2つを優先すると効果が大きい（それぞれエスカレーション基準とRED判定の根拠になり、ヒアリングでの代替が難しい）。
- **形式は問わない**ことを伝える。Word / PDF / Excel / スクリーンショット / 本文の貼り付けのいずれでも取り込める。
- **部分的でよい**ことを伝える。主要な取引形態1つ分だけでも、その類型の基準は裏付けられる。
- **社外秘の扱いに触れる。** 取り込んだ資料は当該作業の範囲でのみ扱い、生成物には取引先名・案件名・個人名を残さない。
- **所要の目安を伝える。** 資料なしでヒアリングのみの場合、共通の質問は40問程度（該当する契約類型ごとに追加）。一括フォームをファイルで配布すれば分担して記入できる。

### 資料が見つからない場合の案内
- 規程の所在が分からない場合は、法務・総務・経営企画のいずれかに「契約審査基準」「決裁規程」があるかを確認するよう案内する。
- 契約管理システムが分からない場合は、コネクタ接続の有無をこちらで確認し、無ければ台帳やフォルダでの代替を案内する。
- 事例集が無い場合は、`interview-guide.md`「事例が無い場合の聴取」で対話から引き出す。

## 収集する6系統

| 系統 | 必須 | 得られるもの | 主な反映先 | 取得手段 |
|---|---|---|---|---|
| ① ヒアリング | **必須** | 自社方針、リスク許容度、エスカレーション体制 | §1、全体 | 対話（`interview-guide.md`） |
| ② 社内規程・既存基準書・契約書雛形 | 推奨 | 既に承認済みの基準値、決裁権限、自社の標準条項と扱っている契約類型 | §1.2、§2.x、スコープ | ファイル添付 / ドキュメントストレージ系コネクタ |
| ③ 過去契約・交渉実績 | 推奨 | 実際に妥結した条件のレンジ、頻出する相手方要求 | §2.x の許容範囲・フォールバック | 契約管理システム / 台帳 / ファイル添付 / メール |
| ④ インシデント・トラブル事例 | 推奨 | 実際に損害・紛争が生じた条件、判断の失敗 | §2.x の許容できない条件、§1.2、§3 RED、§4 Tier 1 | 事例集 / 監査報告 / ヒアリング |
| ⑤ 法令・強行規定 | 推奨 | 譲歩できない下限、必須条項 | §2.x、追加条項 | 法令検索コネクタ（e-Gov） |
| ⑥ レビュー実績・版更新記録 | モードB-2 で**必須** | 明文化されていない論点、守られていない基準 | §2.x の新設・明確化、§3、§4、§5 | 契約管理システムのレビュー記録・版更新の変更理由 |

**モード別の収集範囲:** モードA と モードB-1 は6系統すべてを収集対象とする。モードB-2 は ⑥ を主たる根拠とし、緩和判断の突き合わせに ③ ④ を使う。**B-1 で「改定された規程だけを見る」ように範囲を狭めてはならない。**

**優先順位:** ヒアリングで明示された自社方針 > 社内規程 > 過去実績 > 一般的な商慣行。ただし**法令上の強行規定は常に最優先**とし、これに反する基準は設定しない。

**③と④が矛盾する場合:** 「実績では許容されている条件」と「その条件で損害が生じた事例」が併存する場合、**④を優先して厳格化の方向で提案**し、採否はユーザーに判断させる。③は「過去に締結できた」という事実であり、それが望ましかったことを意味しないため（`3.4 実績の扱いに関する禁止事項`）。

**⑥の位置づけ:** ⑥は自社の**レビュー判断の履歴**であり、③（締結された条件の結果）とも④（生じた損害）とも異なります。緩和方向にも厳格化方向にも解釈できるため、緩和に使う場合は必ず④と突き合わせる。収集・分析の手順は `review-record-analysis.md` に分離しています（`SKILL.md` から直接参照）。

## 1. ヒアリング

`interview-guide.md` の質問項目に沿って対話で収集する。

- セクション単位（基本方針 → 条項別基準 → 重大度 → 優先順位）で順に確認し、一度に大量の質問を投げない。
- ③で集計した実績レンジ、④で整理した事例を提示しながら質問し、ユーザーが判断しやすくする。
- 「ケースバイケース」との回答は、**判定可能な条件に分解**する。分解できない場合は `※要確認` とする。

## 2. 社内規程・既存基準書・契約書雛形

### 対象文書の例
- 契約審査基準・契約管理規程
- 決裁規程・職務権限規程（エスカレーション基準の裏付けになる）
- 購買規程・外注管理規程
- 情報セキュリティ規程・個人情報保護規程（§2.4 の裏付け）
- 過去のレビューメモ、法務からの指摘集
- **自社の契約書雛形（テンプレート）** — 業務委託契約書、NDA、利用規約、発注書など

### 取得フロー
1. **取得手段の確認:** ファイル添付か、ドキュメントストレージ系コネクタ（Google Drive / SharePoint / Salesforce / 契約管理システムのテンプレート等）からの取得かを確認する。
2. **取り込み:** .docx / PDF / Markdown 等からテキストを抽出する。スキャン画像等でテキスト化できない場合は、該当箇所の直接入力を依頼する。
3. **基準値の抽出:** 契約条件に関する数値・条件・決裁ラインを抽出し、**出典（規程名・条番号、または雛形名）を記録**する。
4. **矛盾の確認:** 規程間、または規程と雛形で基準が食い違う場合は、どちらを採用するかをユーザーに確認する。勝手に一方を採用してはならない。

### 契約書雛形からの抽出観点

雛形は「自社が標準として使ってきた条件」であり、**事実上の自社基準**として扱えます。ただし承認済みの基準とは限らないため、採否は必ずユーザーに確認します。

| 観点 | 得られるもの | 反映先 |
|---|---|---|
| **雛形が存在する契約類型** | 自社が扱っている取引形態の実体。ヒアリングの棚卸しより正確なことがある | セクション1.1 の取引形態、`interview-guide-by-type.md` で追加する質問の特定 |
| **雛形に書かれている条項の構成** | 自社が標準的に置いている条項。§2.7 以降に追加すべき条項の判断材料 | §2.x のスコープ、§2.7以降 |
| **雛形の条項に含まれる数値・条件** | 賠償上限の月数、契約期間、通知期間、報告期限など、現行の標準値 | §2.x の自社基準の初期値候補 |
| **雛形に無い条項** | 明文化されていない論点。トラブルの温床になり得る | スコープ漏れの検出 |
| **立場ごとの雛形の差** | 委託者版・受託者版の両方がある場合、立場別の基準がすでに存在する | §2.x の立場別の書き分け |
| **雛形の最終更新時期** | 古い雛形は法改正に未対応の可能性がある | 陳腐化の指摘、§2.4・§2.5 の見直し |
| **雛形が存在しない類型** | 相手方雛形をベースにしている＝交渉力が弱い可能性 | §4 の Tier 配置、§1.1 の交渉スタンス |

**【注意】** 雛形の記載を自動的に自社基準として確定してはならない。「現在の雛形ではこうなっています」という事実として提示し、維持するか見直すかをユーザーに判断させる。根拠種別は「社内規程」として扱い、出典に雛形名を記録する。

**【注意】** 雛形が相手方から提供されたものである場合、自社基準の根拠にしてはならない。自社が作成した雛形かどうかを確認する。

**【注意】** 社内規程・雛形の記述をそのままプレイブックへ転記する際も、契約レビューで判定可能な形（数値・条件）に落ちているかを確認する。落ちていない場合はヒアリングで具体化する。

## 3. 過去契約・交渉実績からの抽出

**実際に締結された条件**は、許容範囲とフォールバックの最も強い裏付けになります。契約管理システムの有無にかかわらず、取得できる経路から収集します。

### 3.1 取得経路

利用可能な経路をユーザーに確認し、複数を併用してよい。**経路によって集計の信頼度が異なる**ため、根拠に出所を記録する。

| 経路 | 得られるもの | 集計の信頼度 | 注意 |
|---|---|---|---|
| **(a) 契約管理システム / CLM系コネクタ** | 締結済み契約の本文、関連契約ツリー、レビュー記録・交渉コメント | 高（本文まで遡れる） | 検索対象カテゴリ・閲覧権限の制約を受ける |
| **(b) 契約管理台帳・スプレッドシート** | 条項ごとの条件が構造化されている場合がある（賠償上限、期間、管轄等） | 高（そのまま集計可） | 記入漏れ・更新遅れがあり得る。**本文と乖離している可能性**があるため、重要条項は本文で裏取りする |
| **(c) ファイル添付（過去契約・レビュー記録）** | 個別契約の実際の文言、過去のレビューメモ | 中（母数が限られる） | 件数が少なく一般化できない場合がある。件数を必ず明示する |
| **(d) メールコネクタ（Gmail / Outlook）** | 交渉経緯、相手方の要求と譲歩の過程、妥結理由 | 低（定量化しにくい） | 個人名・取引先名の除去が必須。定性情報として扱う |
| **(e) 口頭（ヒアリング内で聴取）** | 担当者の記憶による妥結傾向 | — | **件数の裏付けがないため「実績」として扱わない**（下記ルール） |

**【重要 - 出所と件数のルール】**
- 根拠種別を「過去実績」として記録できるのは、**件数を提示できる場合のみ**とする。
- 件数を示せないもの（(e) 口頭、(d) メールからの定性的な印象）は、根拠種別を**「ヒアリング」として記録**する。実績と混同すると、プレイブックの根拠の強さを誤認させるため。
- 台帳（(b)）と本文（(a)(c)）で条件が食い違った場合は**本文を優先**し、台帳の誤りとしてユーザーに報告する。

### 3.2 抽出フロー

1. **対象範囲の決定:** 契約類型（業務委託 / NDA / SaaS / 売買等）と自社の立場、対象期間（例: 直近2年）をユーザーと決める。件数が多すぎる場合は主要類型に絞る。
2. **経路ごとの収集:**
   - **(a) システム:** 対象類型の締結済み契約を検索し、候補一覧をユーザーに提示する。関連契約ツリー（基本契約 → 個別契約 → 変更契約書）を取得する。**変更覚書は「一度合意した条件が後から変更された履歴」であり、実際の落としどころを知る手がかりになる**ため優先的に確認する。
   - **(b) 台帳:** 台帳を取り込み、条項に対応する列を特定する。集計対象の期間・類型で絞り込む。
   - **(c) 添付:** 受領したファイルから該当条項の文言を抽出する。
   - **(d) メール:** 契約名・当事者・条項キーワードで検索し、交渉経緯を抽出する。
3. **交渉経緯の取得:** 「相手方が要求した条件」「社内で懸念された点」「最終的に妥結した理由」を抽出する。(a) ではレビュータスクのコメント・添付資料、(d) ではメール本文が情報源となる。
4. **条項ごとの値の集計:** 条項別に実績値を並べ、最頻値・最小値・最大値と件数を集計する。**経路別の内訳も記録する**（例: 台帳12件 + 本文確認3件）。
5. **例外の切り分け:** 相手方が圧倒的に優位な取引、一度限りの特殊案件は標準基準に含めず、**例外として注記**する。
6. **匿名化:** プレイブックへ反映する時点で、取引先名・案件名・個人名を除去し一般化する（`playbook-schema.md`「5. 匿名化の要件」）。

### 3.3 集計する代表的な項目

| 条項 | 集計する値 |
|---|---|
| 損害賠償の制限 | 上限の算定基礎（月数 / 定額）、上限なしの件数、除外事由の内容 |
| 補償 | 補償の相互性、対象範囲、責任上限の適用有無 |
| 知的財産権 | 帰属先、著作権法27条・28条の明記有無、ライセンス範囲 |
| データ保護 | 再委託の可否形式（事前承諾 / 事前通知）、事故報告期限、終了時の取扱い |
| 契約期間・解除 | 当初期間、更新拒絶の通知期限、中途解約の予告期間、反社条項の有無 |
| 準拠法・紛争解決 | 準拠法、管轄裁判所、仲裁の有無 |

### 3.4 実績の扱いに関する禁止事項

- **【禁止】** 実績の最頻値を、ユーザーの判断を経ずに「自社基準」として確定してはならない。実績は**判断材料として提示**するに留める。
- **【禁止】** 実績が1〜2件しかない条項を一般化してはならない。件数不足を明示し、ヒアリングでの方針決定に委ねる。
- **【禁止】** 「実績があるから許容範囲」と結論づけてはならない。過去に不利な条件で締結してしまった事例が含まれる可能性があるため、**望ましくない実績かどうかをユーザーに確認**する。④のインシデント事例と突き合わせ、損害が生じた条件が実績に含まれていないかを確認する。

> 4. **交渉経緯の取得:** `list_comment`（`resource_type="TASK"`、`resource_id` にレビュータスクのID）でレビュータスクのコメントを取得する。レスポンスに `attachmentFiles` が含まれる場合、`download_attachment` で相手方からの修正依頼・交渉経緯資料を取得する。契約書に直接添付された資料は `list_attachment_files` で一覧を取得する（コメント添付は含まれない）。
> 5. **制約:** ダウンロードURLの有効期限は300秒（5分）。期限切れの場合は再取得する。閲覧権限がない契約は一覧が空・ダウンロードが403となる。

## 4. インシデント・トラブル事例からの抽出

過去に**実際に損害・紛争・指摘が生じた事例**は、「許容できない条件」とエスカレーション基準の最も強い裏付けになります。③（妥結レンジ）が許容範囲を広げる方向の材料であるのに対し、④は**基準を厳格化する方向**の材料です。

### 4.1 対象となる事例

| 分類 | 例 |
|---|---|
| 契約起因の紛争・クレーム | 賠償範囲を巡る争い、成果物の権利帰属を巡る争い、解約時のトラブル |
| 情報漏洩・セキュリティ事故 | 委託先からの個人情報漏洩、再委託先での事故、報告遅延 |
| 法令違反・行政指摘 | 下請法違反の指摘、優越的地位の濫用に関する指摘、内部監査の所見 |
| 履行段階の問題 | 支払遅延、納期遅延、品質不良、想定外の追加負担 |
| 知財関連 | 第三者からの侵害クレーム、ライセンス範囲の逸脱 |

### 4.2 取得経路

| 経路 | 内容 |
|---|---|
| **事例集・ヒヤリハット集の添付** | 法務・リスク管理部門が整備した事例集（.docx / PDF / スプレッドシート）を受領する |
| **監査・リスク管理報告** | 内部監査報告書、リスクアセスメント結果、コンプライアンス報告 |
| **インシデント管理システム / 台帳** | インシデント管理台帳、クレーム管理台帳をコネクタまたは添付で取得する |
| **契約管理システムの記録** | 紛争・解約に至った案件のレビュー記録・コメント（経路(a) と同じ手段） |
| **ヒアリング** | 事例集が未整備の場合、「過去にトラブルになった条件」を対話で聴取する |

### 4.3 事例から基準への変換

事例そのものをプレイブックに書き写してはならない。**原因を条項レベルの条件に変換**して反映する。

| 事例の原因 | プレイブックの反映先 |
|---|---|
| 必要な条項が契約に無かった | §2.x の自社基準に必須条項として追加。該当節が無ければ §2.7 以降に追加条項を新設 |
| 条項はあったが基準が甘かった | §2.x の「許容できない条件」を厳格化（境界値の引き上げ） |
| 判断を誤り、エスカレーションしなかった | §1.2 のエスカレーション基準に条件を追加。§3 の RED 具体例に追加 |
| 相手方の要求を受諾したことが原因 | §4 の Tier 1（Deal Breakers）へ昇格を検討 |
| 契約書の記載では防げない運用・履行の問題 | **プレイブックには反映しない。** 契約外の運用課題として報告に留める |

**変換例**

```
【事例】委託先からの個人情報漏洩。契約に再委託の制限がなく、把握していない再委託先で事故が発生。報告が事故発覚から5日後だった。
↓
【反映1】§2.4 許容できない条件に「無制限な再委託の許可」を追加（既存であれば境界を維持）
【反映2】§2.4 自社基準の漏洩事故の報告期限を「発覚後24時間以内」に設定、許容範囲を48時間までに限定
【反映3】§1.2 エスカレーション基準に「再委託の包括同意を求められた場合」を追加
【反映4】§3 RED の具体例に「個人情報を扱うのに再委託制限がない」を追加
```

### 4.4 事例の扱いに関するルール

- **過剰反応を避ける。** 1件のインシデントを根拠に全社基準を過度に厳格化してはならない。**発生頻度と影響度**を提示し、基準に反映するか例外として注記するかをユーザーに判断させる。
- **ただし重大類型は1件でも反映してよい。** 法令違反、個人情報漏洩、反社リスク、人身損害など影響が重大な類型は、1件でも §3 RED / §4 Tier 1 への反映を提案する。
- **契約書で防げない事例を条項化しない。** 履行・運用段階の問題（担当者の連絡漏れ、社内手続の不備等）を無理に条項に落とすことは、推測で基準を作ることと同じである。契約外の課題として区別して報告する。
- **匿名化を徹底する。** 事例は取引先名・案件名・担当者名を含みやすい。プレイブックに反映する時点で必ず一般化する（`playbook-schema.md`「5. 匿名化の要件」）。
- **未解決の紛争は扱いを確認する。** 係争中の案件は情報の取扱いに制約がある場合があるため、プレイブックへの反映可否をユーザーに確認する。

## 5. 法令・強行規定

「e-Gov」法令検索コネクタが使用できる場合、基準の下限となる法令要件を取得する。

### 確認すべき代表的な法令
| 領域 | 法令 | プレイブックへの反映先 |
|---|---|---|
| 委託取引 | 下請法（支払期日、書面交付、禁止行為） | §2.5、追加条項（下請法対応） |
| 個人情報 | 個人情報保護法（委託先監督、越境移転） | §2.4 |
| 取引条件 | 独占禁止法（優越的地位の濫用） | §1.1、§2.2 |
| 契約一般 | 民法（契約不適合責任、解除、消滅時効） | §2.1、§2.5 |
| 著作権 | 著作権法（第27条・第28条、著作者人格権） | §2.3 |

### 反映のルール
- 法令由来の要件は、**フォールバック不可の下限**として明記する（例: 「下請法適用取引では支払期日は受領後60日以内。これを超える条件は法令違反のため受諾不可」）。
- 条文を引用する場合は**条番号を明示**し、取得した条文に基づいて記載する。条文を確認できない場合は「※要確認（条文未確認）」と付す。
- 法令の適用可否（例: 下請法の資本金要件）が判断できない場合は、適用条件そのものをプレイブックに記載し、レビュー時に判定できるようにする。
- ④で法令違反の指摘事例がある場合は、該当法令を優先的に確認し、指摘の再発を防ぐ条件を §2.x に反映する。

## 6. 情報源が得られない場合

| 状況 | 対応 |
|---|---|
| 契約管理システムが無い | 台帳・ファイル添付・メール（経路(b)(c)(d)）で代替する。いずれも無ければヒアリングのみで構築し、実績由来の許容範囲は `※要確認` とする |
| 台帳はあるが条項の条件が記録されていない | 台帳から対象契約を特定し、本文をファイル添付で受領して裏取りする。件数が確保できない場合は一般化しない |
| インシデント事例集が未整備 | ヒアリングで「過去にトラブルになった条件」を聴取する。件数の裏付けがないため、根拠種別は「ヒアリング」として記録する |
| 社内規程が未整備 | ヒアリングで方針を確定する。確定できない項目は `※要確認` を残す |
| ヒアリング対象者が不明 | エスカレーション先・承認者が定義できないため、`§1.2 エスカレーション基準` を `※要確認` とし、決定を促す |
| いずれも不足 | 一般的な商慣行を**暫定値**として置き、`※要確認（一般的な商慣行に基づく暫定値）` と明示する。確定値として扱ってはならない |
