# インプット（根拠情報）

> プレイブックの基準を裏付ける根拠情報の定義。**利用可能な情報源だけを使い、使えない系統を推測で補完しない**ことが原則です。収集・分析の具体的な手順は定義しません（出力仕様である `playbook-schema.md` の要件を満たすために必要な集計・整理を、その場で判断してください）。

---

## 0. 事前に用意すると良いインプット（モードA・B-1、初回向け）

**利用者はプレイブックを作った経験がないことが多いため、何を渡せばよいかを先に示します。** 以下をそのまま提示してよい（`SKILL.md` ステップ1.2）。**モードB-1 でも同じインプットを受け付けます。**

| 用意するもの | どこにあるか | あると何が良くなるか |
|---|---|---|
| **契約審査基準・契約管理規程** | 法務部門の規程集、社内ポータル | 既に承認済みの基準をそのまま使えるため、決め直しが不要になる |
| **自社の契約書雛形（テンプレート）** | 法務部門、共有フォルダ、契約管理システムのテンプレート、Google Drive / SharePoint | **どの契約類型を扱っているかが分かり、質問すべき類型を特定できる**。雛形の条項が事実上の自社基準になっているため、基準の初期値として使える |
| **決裁規程・職務権限規程** | 総務・経営企画部門 | エスカレーションの金額しきい値と承認者が確定する |
| **過去の契約書（主要な取引形態ごとに5〜10件）** | 契約管理システム、共有フォルダ | 実際に妥結した条件から許容範囲とフォールバックを裏付けられる |
| **契約管理台帳（Excel等）** | 法務・購買部門 | 賠償上限や契約期間が列で入っていれば、契約書を開かずに集計できる |
| **トラブル事例集・インシデント台帳** | 法務、リスク管理、内部監査部門 | 「許容できない条件」とRED判定の根拠になる。最も価値が高い |
| **情報セキュリティ規程・個人情報保護規程** | 情報システム、法務部門 | データ保護条項の基準が確定する |
| **過去のレビューメモ・法務の指摘集** | 法務担当者の手元、メール | 繰り返し指摘している論点を基準に格上げできる |

### 伝え方のルール
- **すべて任意で、形式も問わない**（Word / PDF / Excel / スクリーンショット / 本文の貼り付け）。1つも無くてもヒアリングだけで作成できる。**部分的でよい**（主要な取引形態1つ分だけでも、その類型の基準は裏付けられる）。
- **優先順位を示す。** 揃えるのが難しい場合は「決裁規程」と「トラブル事例集」の2つを優先すると効果が大きい（それぞれエスカレーション基準とRED判定の根拠になり、ヒアリングでの代替が難しい）。
- **社外秘の扱いに触れる。** 取り込んだ資料は当該作業の範囲でのみ扱い、生成物には取引先名・案件名・個人名を残さない。
- **所要の目安を伝える。** 資料なしでヒアリングのみの場合、確認事項は100問程度になる。一括フォームをファイルで配布すれば分担して記入でき、わからない項目は「保留」と書いて飛ばせる。
- **法令の要件は聞かない。** 法令で下限が定まっている項目は、ユーザーに数値を決めさせず「e-Gov」法令検索コネクタで取得する。ヒアリングでは「法令の要件を満たす前提でよいか」と、それを上回る自社の追加要件があるかだけを確認する。
- 規程・システムの所在が分からない場合は、法務・総務・経営企画への確認や、台帳・フォルダでの代替を案内する。事例集が無い場合は「過去にトラブルになった条件」を対話で聴取する。

## 1. 収集する6系統

| 系統 | 必須 | 得られるもの | 主な反映先 |
|---|---|---|---|
| ① ヒアリング | **必須** | 自社方針、リスク許容度、エスカレーション体制 | §1、全体 |
| ② 社内規程・既存基準書・契約書雛形 | 推奨 | 既に承認済みの基準値、決裁権限、自社の標準条項と扱っている契約類型 | §1.2、§2.x、スコープ |
| ③ 過去契約・交渉実績 | 推奨 | 実際に妥結した条件のレンジ、頻出する相手方要求 | §2.x の許容範囲・フォールバック |
| ④ インシデント・トラブル事例 | 推奨 | 実際に損害・紛争が生じた条件、判断の失敗 | §2.x の許容できない条件、§1.2、§3 RED、§4 Tier 1 |
| ⑤ 法令・強行規定 | 推奨 | 譲歩できない下限、必須条項 | §2.x、追加条項 |
| ⑥ レビュー実績・版更新記録 | モードB-2 で**必須** | 明文化されていない論点、守られていない基準 | §2.x の新設・明確化、§3、§4、§5 |

**モード別の収集範囲:** モードA と モードB-1 は6系統すべてを収集対象とする。モードB-2 は ⑥ を主たる根拠とし、緩和判断の突き合わせに ③ ④ を使う。**B-1 で「改定された規程だけを見る」ように範囲を狭めてはならない**（改訂内容の妥当性は他の材料でも裏付ける必要があるため）。

**優先順位:** ヒアリングで明示された自社方針 > 社内規程 > 過去実績 > 一般的な商慣行。ただし**法令上の強行規定は常に最優先**とし、これに反する基準は設定しない。

**③と④が矛盾する場合:** 「実績では許容されている条件」と「その条件で損害が生じた事例」が併存する場合、**④を優先して厳格化の方向で提案**し、採否はユーザーに判断させる。③は「過去に締結できた」という事実であり、それが望ましかったことを意味しないため。⑥は緩和方向にも厳格化方向にも解釈できるため、緩和に使う場合は必ず④と突き合わせる。

## 2. 系統ごとの注意点

根拠の記載要件（件数と出所の併記、5種別の分類）は `playbook-schema.md` §4 に従う。以下は取り違えやすい点のみを定義する。

**② 契約書雛形**
- 雛形は「自社が標準として使ってきた条件」であり事実上の自社基準として扱えるが、**承認済みの基準とは限らない**。「現在の雛形ではこうなっています」という事実として提示し、維持するか見直すかをユーザーに判断させる。根拠種別は「社内規程」とし、出典に雛形名を記録する。
- **相手方から提供された雛形は自社基準の根拠にしてはならない。** 自社が作成したものか確認する。
- 規程間、または規程と雛形で基準が食い違う場合は、どちらを採用するかをユーザーに確認する。勝手に一方を採用してはならない。

**③ 過去実績**
- **【禁止】** 実績の最頻値を、ユーザーの判断を経ずに「自社基準」として確定してはならない。実績は**判断材料として提示**するに留める。
- **【禁止】** 実績が1〜2件しかない条項を一般化してはならない。件数不足を明示する。
- **【禁止】** 「実績があるから許容範囲」と結論づけてはならない。過去に不利な条件で締結してしまった事例が含まれる可能性があるため、④と突き合わせる。
- 契約管理台帳と契約本文で条件が食い違った場合は**本文を優先**し、台帳の誤りとしてユーザーに報告する。
- 相手方が圧倒的に優位な取引、一度限りの特殊案件は標準基準に含めず**例外として注記**する。

**④ インシデント事例**
- 事例そのものを書き写さず、**原因を条項レベルの条件に変換**して反映する（条項の欠落 → 必須条項の追加 / 基準の甘さ → 境界値の引き上げ / エスカレーション漏れ → §1.2 と §3 RED / 相手方要求の受諾 → §4 Tier 1 への昇格）。
- **契約書の記載では防げない運用・履行段階の問題は反映しない。** 契約外の課題として報告に留める。
- **1件のインシデントで全社基準を過度に厳格化してはならない。** ただし法令違反・情報漏洩・反社リスク・人身損害は1件でも §3 RED / §4 Tier 1 への反映を提案してよい。
- **係争中・調査中の案件は、反映可否をユーザーに確認する。**

**⑥ レビュー実績・版更新記録（モードB-2）**
- 分析対象は、レビュータスクとそのコメント、タスクコメントの添付資料、版更新の変更理由、契約本文の版間差分。対象期間の起点は**プレイブックの最終更新日時**（`playbook-schema.md` §2）。
- `review-contract` は版更新時に、レビューの目的・主要な修正箇所とその意図・ユーザーが最終的に加えた判断をまとめた更新コメントを登録する。これが最も情報量の多い入力。**バージョン履歴を読み出せない場合は、同じ内容がレビュー完了コメントに残っている。**
- 改訂候補として扱う件数のしきい値は `update-policy.md` §5。

## 3. 法令・強行規定（⑤）

**「e-Gov」法令検索コネクタで条文を都度取得する。** 使用できない場合は `※要確認（条文未確認）` と付し、**推測で数値を書かない**。

### 見落としやすい規制フック

**適用の有無だけを確認し、条文の内容はe-Govで取得する。** 自動的には想起しにくく、抜けると法令違反に直結する項目。

| 領域 | 確認するフック |
|---|---|
| 下請法 | 適用判定（資本金区分 × 取引類型）、支払期日、発注書面の記載事項、書類の保存、禁止行為への該当 |
| フリーランス法 | 特定受託事業者との取引か、取引条件の明示義務の履行方法 |
| 労働者派遣法・職業安定法 | 派遣可能期間と抵触日通知、指揮命令者の特定、派遣と請負の区分（偽装請負の回避） |
| 個人情報保護法 | 委託 / 共同利用 / 第三者提供のどの整理か、越境移転の根拠、漏洩時の本人通知・当局報告の責任分担 |
| 独占禁止法 | 再販売価格の拘束、競合品取扱制限、テリトリー制限、優越的地位の濫用に当たる要求 |
| 建設業法 | 一括下請の禁止、書面の記載事項、見積期間 |
| 輸出管理・経済制裁 | 該非判定の責任、denied party スクリーニング、再輸出の制限 |
| 業規制 | 金融の外部委託先管理、医療の情報安全管理ガイドライン、電気通信の通信の秘密、薬機法・医療広告 |
| 贈収賄防止 | 公務員が関与する取引か、外国公務員贈賄・FCPA / UKBA の適用可能性 |
| OSS・知財 | 使用を禁じるライセンス種別、SBOMの要求、第三者権利の非侵害保証と調査範囲 |

### 反映のルール
- 法令由来の要件は**フォールバック不可の下限**として明記する。ただし**条文の数値をプレイブックに転記しない**（法改正で陳腐化するため）。「法令の下限を満たすこと」と、**適用されるかどうかの判定条件**を書く（例: 「下請法の適用取引では支払期日を法定の上限内とする。適用条件は資本金区分と取引類型で判定」）。
- 自社が法令の下限より厳しい基準を持つ場合は、**その追加要件だけ**を数値で書く（例: 「法令の下限に加え、自社は検収後30日以内を求める」）。
- 法令の適用可否が判断できない場合は、適用条件そのものをプレイブックに記載し、レビュー時に判定できるようにする。
- ④で法令違反の指摘事例がある場合は、該当法令を優先的に確認し、指摘の再発を防ぐ条件を §2.x に反映する。
- **法令の解説を蓄積しない。** 参照ファイルにもプレイブックにも、法令の一般的な説明は書かない。

## 4. 契約管理システムからの取得（ContractS CLM 利用時）

ツール名と引数はMCPのスキーマに従う。**スキーマから読み取れない制約**を以下に定義する。

- `search_documents` の検索対象は `ORIGINAL`（原契約書）カテゴリの**締結済み契約に限られる**。
- 関連契約ツリー（基本契約 → 個別契約 → 変更契約書）は、`search_documents` のレスポンスの `contractId` を `get_related_contracts` に渡して取得する。**変更覚書は「一度合意した条件が後から変更された履歴」であり、実際の落としどころを知る手がかりになる**ため優先的に確認する。
- レビュータスクのコメントは `list_task_comment`（`resource_type="TASK"`、`resource_id` にタスクID）。レスポンスの `attachmentFiles` は `download_attachment` で取得する。**契約書に直接添付された資料は `list_attachment_files` で取得し、コメント添付は含まれない。**
- ダウンロードURLの**有効期限は300秒**。期限切れの場合は再取得する。
- 閲覧権限がない契約は一覧が空・ダウンロードが403となる。
{% if platform == 'copilot' %}
- 本文の取得は `download_document` で得たダウンロードURLをユーザーに提示し、ダウンロードしたファイルをチャットに添付するよう促す（`type: "docx"`, `finalized_review_download: false`）。必ずURLをハイパーリンクで表示する。Curl 等による直接ダウンロードはサンドボックスの外部通信制限で不可。
{% else %}
- 本文の取得は `download_document`（`type: "docx"`, `finalized_review_download: false`）。
{% endif %}

## 5. 情報源が得られない場合

| 状況 | 対応 |
|---|---|
| 契約管理システムが無い | 台帳・ファイル添付・メールで代替する。いずれも無ければヒアリングのみで構築し、実績由来の許容範囲は `※要確認` とする |
| 台帳はあるが条項の条件が記録されていない | 台帳から対象契約を特定し、本文をファイル添付で受領して裏取りする。件数が確保できない場合は一般化しない |
| インシデント事例集が未整備 | ヒアリングで「過去にトラブルになった条件」を聴取する。件数の裏付けがないため、根拠種別は「ヒアリング」として記録する |
| 社内規程が未整備 | ヒアリングで方針を確定する。確定できない項目は `※要確認` を残す |
| ヒアリング対象者が不明 | エスカレーション先・承認者が定義できないため、§1.2 を `※要確認` とし、決定を促す |
| いずれも不足 | 一般的な商慣行を**暫定値**として置き、`※要確認（一般的な商慣行に基づく暫定値）` と明示する。確定値として扱ってはならない |
